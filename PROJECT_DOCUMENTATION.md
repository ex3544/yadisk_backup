## 1. Общее описание и реальное назначение

Проект **Yandex.Disk Backup** предназначен для комплексной выгрузки данных из облачного хранилища Яндекс.Диск перед закрытием подписки или миграцией на локальные NAS / альтернативные облака.

В отличие от стандартных клиентов, инструмент решает две принципиально разные задачи:
1. **Выгрузка файлового диска:** скачивание обычных файлов через публичный REST API по OAuth-токену.
2. **Выгрузка безлимитного мобильного хранилища («Photoslice»):** скачивание фото и видео, загруженных со смартфонов, которые не занимают квоту на диске и не видны в стандартном API диска.

## 2. Архитектура системы и модули

Система разделена на независимые модули, работающие через две раздельные базы данных SQLite в режиме WAL (Write-Ahead Logging):

```
┌─────────────────────────────────────────────────────────────┐
│             Web UI (FastAPI) & CLI (main.py)                │
└──────────────┬──────────────────────────────┬───────────────┘
               │                              │
      [Обычный Диск]                     [Безлимит Photoslice]
               │                              │
      downloader.py                   unlim_download.py
      (REST API + SDK)                (Web API: models-v2)
               │                              │
               ▼                              ▼
            state.db                   unlim_state.db
        (таблица: files)          (unlim_files, unlim_clusters)
               │                              │
        ThreadPoolExecutor             unlim_worker.py (1..N)
        (до 5 потоков)                (bulk-download ZIP)
               │                              │
               └──────────────┬───────────────┘
                              ▼
                     DOWNLOAD_DIR (файлы)
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
                dedupe.py          organize.py
             (очистка state.db)  (сортировка по типам/датам)
```

### Основные компоненты:
* **`main.py`** — точка входа CLI для работы с обычным диском (`scan`, `download`, `retry-failed`, `stats`, `verify`).
* **`downloader.py`** — движок сканирования (BFS обход дерева каталогов) и многопоточного скачивания через `yadisk.Client`.
* **`state.py`** — ORM/обёртка над SQLite (`state.db`) с пулом соединений на поток через `threading.local`.
* **`unlim_download.py`** — эмулятор веб-клиента Яндекс.Диска. Парсит сессионные cookies, запрашивает снимок галереи (`photoslice`) и формирует каталог файлов по дням.
* **`unlim_worker.py`** — параллельный воркер выгрузки безлимита. Забирает файлы пачками по 250 штук, формирует ZIP на сервере Яндекса и распаковывает локально.
* **`dedupe.py`** — вспомогательный скрипт дедупликации в базе `state.db`.
* **`organize.py`** — раскладчик файлов по папкам типов (`Фото`, `Видео`, `Документы` и т.д.) и календарным годам/месяцам.
* **`webui.py`** — панель управления на FastAPI с мониторингом прогресса, управлением подпроцессами и CSRF-защитой.
* **`launcher.py`** — оконная обёртка установленной версии: локальный сервер, WebView2, трей, сворачивание в трей и запуск воркеров через multi-call.
* **`watch.py`** — консольный терминальный монитор в реальном времени.
* **`utils.py`** — санитизация путей, потоковый расчёт MD5, поддержка длинных путей Windows (`\\?\`).

## 4. Что проект делает НА САМОМ ДЕЛЕ (Реальность vs Описание)

### 1. Скачивание обычного диска — Работает надежно
* Заявленное поведение соответствует коду: обход BFS, параллельное скачивание до 5 потоков, докачка (resume) при совпадении размера файла.
* Прогресс действительно персистентен благодаря `state.db`.

### 2. Безлимит (Photoslice) — Хрупкий реверс-инжиниринг веб-морды
* Это **не официальный API**, а внутренняя механика веб-версии Яндекс.Диска (`models-v2`).
* Авторизация работает через сессионные куки (`Session_id`, `yandexuid`). Куки живут ограниченное время (от нескольких часов до нескольких дней). Если сессия истекает посередине скачивания многогигабайтного архива, воркеры останавливаются.
* Токены `sk` и `uid` извлекаются регулярными выражениями из HTML страницы `disk.yandex.ru`. Любое косметическое изменение Яндексом верстки приведет к поломке скрипта.
* **Внимание:** В ветке `main` безлимит запускать **нельзя**, так как из-за бага пропущенные Яндексом файлы считаются скачанными. В ветке `fix/audit-2026-08` эта проблема устранена.

### 3. Скрипт `dedupe.py` — Скрытая опасность удаления файлов
* Несмотря на безобидное название «Дедупликация», скрипт **принудительно удаляет из очереди базы данных все не-медиа файлы** (`DELETE FROM files WHERE remote_path = ?` для всех расширений, не являющихся фото/видео).
* Если пользователь сначала сделает `scan`, затем запустит `dedupe.py`, а потом `download`, он скачает только фото и видео. Все документы (`.docx`, `.pdf`), архивы (`.zip`) и программы будут стёрты из плана скачивания!

### 4. Сортировка `organize.py` — Наивное определение дат
* Определение дат для раскладывания по папкам `ГГГГ/ГГГГ-ММ` опирается исключительно на имя файла (регулярные выражения типа `IMG_20240815`).
* Скрипт **не читает EXIF-метаданные** из заголовков JPEG/HEIC. Если в имени файла даты нет, он берет время модификации файла на диске (`mtime`), которое часто равно моменту скачивания файла, а не дате съёмки.

## 5. Детальный разбор компонентов

### Слой сетевых ретраев (`downloader.py`)
```python
# Логика в fix/audit-2026-08:
NON_RETRYABLE = (
    yadisk.exceptions.UnauthorizedError,
    yadisk.exceptions.ForbiddenError,
    yadisk.exceptions.PathNotFoundError,
)

def _is_retryable(exc: BaseException) -> bool:
    if isinstance(exc, NON_RETRYABLE):
        return False
    if isinstance(exc, yadisk.exceptions.YaDiskError):
        return True
    return isinstance(exc, (OSError, ConnectionError, TimeoutError))
```
В ветке `fix` повторные попытки происходят только при временных сбоях соединения или ошибках 5xx. На ошибку 429 сервер берет принудительную паузу на 60 секунд.

### Безопасная распаковка ZIP (`unlim_worker.py`)
```python
def safe_extract_dst(base_dir: str, member_name: str) -> str | None:
    raw = member_name.replace("\\", "/")
    parts = [p.strip() for p in raw.split("/") if p.strip() and p not in (".", "..") and ":" not in p]
    if not parts:
        return None
    dst = os.path.join(base_dir, *parts)
    base_real = os.path.realpath(base_dir)
    dst_real = os.path.realpath(dst)
    if os.path.commonpath([base_real, dst_real]) != base_real:
        return None
    return dst
```
Данная функция гарантирует, что ни один файл из сгенерированного сервером архива не выйдет за пределы целевой папки `_unlim`.

## 6. Инструкция по безопасному использованию

Для гарантированного сохранения всех данных соблюдайте следующий порядок:

### Шаг 0. Переключение на исправленную ветку
```bash
git checkout fix/audit-2026-08
```

### Шаг 1. Установка зависимостей
```bash
python3 -m pip install -r requirements.txt
```

### Шаг 2. Скачивание обычного диска (CLI)
1. Создайте `.env` файл на основе `.env.example`:
   ```ini
   YA_DISK_TOKEN=<ваш OAuth-токен>
   DOWNLOAD_DIR=<путь>/YandexBackup
   MAX_WORKERS=4
   ```
2. Проверьте токен:
   ```bash
   python3 main.py check
   ```
3. Просканируйте структуру диска:
   ```bash
   python3 main.py scan
   ```
4. **Не запускайте `dedupe.py`**, если вам нужны документы и прочие не-медиа файлы!
5. Запустите скачивание:
   ```bash
   python3 main.py download --workers 4
   ```
6. В случае сбоев повторите упавшие файлы:
   ```bash
   python3 main.py retry-failed
   ```
7. Выполните проверку целостности по MD5:
   ```bash
   python3 main.py verify
   ```

### Шаг 3. Скачивание безлимита (Photoslice)
1. Зайдите в браузер на `https://disk.yandex.ru/client/photo`.
2. Экспортируйте куки через расширение *Cookie-Editor* в формате JSON и сохраните в корень проекта под именем `cookies.json`.
3. Соберите список файлов:
   ```bash
   python3 unlim_download.py --collect
   ```
4. Запустите воркеры в отдельных терминалах (например, 2-3 воркера):
   ```bash
   python3 unlim_worker.py --id 1
   python3 unlim_worker.py --id 2
   ```
5. Проверьте статус очереди:
   ```bash
   python3 unlim_download.py --status
   ```
6. Если есть сбоившие файлы, верните их в очередь:
   ```bash
   python3 unlim_download.py --retry-failed
   ```

## 7. Реализованные улучшения и аудит-патчи (Октябрь 2026)

Все выявленные остаточные проблемы успешно устранены и покрыты тестами (всего 86 тестов):
1. **Безопасная дедупликация (`dedupe.py`):**
   * Принудительное удаление не-медиа файлов исключено из стандартного пайплайна.
   * Дедупликация работает для **всех** файлов (документы, архивы, фото).
   * Удаление не-медиа вынесено под явный опциональный флаг `--media-only`.
2. **Контроль дискового пространства (`downloader.py`):**
   * Добавлена функция `check_free_space` с запасом 50 МБ.
   * При переполнении диска (`ENOSPC`) загрузка немедленно прерывается, а неначатые файлы остаются в статусе `pending`.
3. **Чтение метаданных EXIF и MP4 (`organize.py`):**
   * Добавлены функции `get_exif_date` и `get_mp4_date` без сторонних бинарных зависимостей.
   * Дата съемки извлекается напрямую из метаданных фото/видео, устраняя сваливание старых фото в дату скачивания.
4. **Устранение коллизий при переименовании файлов Яндексом (`unlim_worker.py`):**
   * В `split_by_extracted` добавлен проход сопоставления по MD5 распакованного файла против хеша в базе `unlim_state.db`.
5. **Повышение стабильности сессии и кроссплатформенности (`webui.py`, `unlim_download.py`):**
   * Добавлены резервные регулярные выражения для `sk` и `uid`.
   * Исправлена кроссплатформенная проверка `_is_safe_organize_path` на Linux.
   * Добавлена защита от межсайтовых атак через заголовок `Sec-Fetch-Site`.

## 8. Автономная сборка и инсталлятор для Windows

Для использования без предварительной установки Python и зависимостей добавлены инструменты сборки:

1. **Интерактивный мастер установки ([`setup_wizard.bat`](setup_wizard.bat)):**
   * Пошаговый опрос в формате «Да / Нет» (`[Y/N]` / `[Д/Н]`).
   * Проверяет Python 3.11+, предлагает установить его через `winget` или открыть официальный установщик.
   * Проверяет и при необходимости устанавливает `pip` и библиотеки из `requirements.txt`.
   * Предлагает собрать автономный `.exe` или сразу запустить приложение.
2. **Сборка единого бинарника ([`build.bat`](build.bat) / [`build_exe.py`](build_exe.py) / [`yadisk_backup.spec`](yadisk_backup.spec)):**
   * Собирает полностью автономный файл `dist/YandexDiskBackup.exe` (~45 МБ).
   * В бинарник вшит Python, все библиотеки, HTML/JS/CSS интерфейс и многофункциональный диспетчер подпроцессов.
   * При старте консоль выводит прямые ссылки на получение OAuth-токена и расширение Cookie-Editor.
3. **Автоматическая сборка в облаке ([`.github/workflows/build-windows.yml`](.github/workflows/build-windows.yml)):**
   * GitHub Actions на виртуальной машине Windows собирает `.exe` при каждом пуше и прикрепляет готовый файл в артефакты репозитория.
4. **Подготовка к установщику (этап 1, 2026-10-26):**
   * [`paths.py`](paths.py) разделяет код (`APP_DIR`) и изменяемые данные (`DATA_DIR`): в установленной версии — `%LOCALAPPDATA%\YandexDiskBackup`, в исходниках — папка проекта; переопределение через `YADISK_DATA_DIR`.
   * [`db_migrations.py`](db_migrations.py) версионирует схему через `PRAGMA user_version`, делает резервную копию перед миграцией и применяет её атомарно.
   * Схема «Безлимита» вынесена в [`unlim_schema.py`](unlim_schema.py), чтобы все процессы использовали одинаковые миграции.
   * Версии зависимостей зафиксированы в [`requirements.txt`](requirements.txt); полный проверенный набор — в [`requirements.lock`](requirements.lock).
5. **Первый запуск и диагностика (этап 2, 2026-10-26):**
   * [`version.py`](version.py) хранит единые название, версию (`35.7.1`) и издателя (`Sergey Pukhir (ex3544, vovapuh's son)`).
   * Мастер первой настройки спрашивает OAuth-токен и две папки; куки и ключ отчётов можно добавить позже. Факт завершения (или «Позже») отмечается файлом `DATA_DIR/.setup_done`.
   * [`profiles.py`](profiles.py) ведёт профили пользователей: реестр
     `BASE_DATA_DIR/profiles.json`, папки `BASE_DATA_DIR/profiles/<id>/`.
     Профиль — отдельный каталог данных (куки, токен, базы, логи, отчёты),
     поэтому переключение — перезапуск с другим `YADISK_DATA_DIR`.

## 9. Прямой высокоскоростной загрузчик Безлимита (`unlim_direct.py`) и учёт статусов

В связи с ограничениями Яндекса на фоновое формирование ZIP-архивов (`mpfs/bulk-download-prepare` часто возвращает HTTP 429 код 394 из-за старых зависших операций в кластере), был разработан модуль **[`unlim_direct.py`](unlim_direct.py)**:

1. **Прямое скачивание оригиналов через `mpfs/url`:**
   * Модуль запрашивает прямые ссылки на скачивание оригинальных медиа-файлов через `mpfs/url` (параметр `disposition=attachment`).
   * Поддерживает как фотографии (`.jpg`, `.heic`, `.png`, `.webp`), так и видеофайлы (`.mp4`, `.mov`).
   * Трафик направляется в обход прокси (`trust_env=False`, очистка прокси-переменных окружения) напрямую с CDN Яндекса (`downloader.disk.yandex.ru`), обеспечивая максимальную скорость провайдера.
2. **Принудительный IPv4 (`urllib3.util.connection`):**
   * Принудительно отключает IPv6 для устранения таймаутов на нодах `*.storage.yandex.net`, вызванных некорректной маршрутизацией IPv6 в виртуальных машинах.
3. **Политика нулевых повторов (Zero-retry Skip):**
   * Если нода Яндекса возвращает HTTP 500 (`file IO failure`) или таймаут, файл **мгновенно пропускается** без циклов повторов и задержек `time.sleep()`.
   * Файл переводится в статус `skipped` с записью точной причины в поле `error`.
   * Это предотвращает блокировку пула потоков на сбойных кластерах и позволяет выжимать максимальную скорость из интернет-канала.
4. **Полный учёт файлов в базе `unlim_state.db`:**
   * Таблица `unlim_files` содержит записи обо всех 47 662 файлах безлимита.
   * `status='downloaded'` — файл успешно скачан, заполнены `local_path`, `size`, `downloaded_at`.
   * `status='skipped'` — файл пропущен из-за ошибки сервера или недоступности ноды; причина зафиксирована в `error`.
   * `status='pending'` — файл ожидает очереди на загрузку.
   * По завершении основного потока все пропущенные файлы можно проверить запросом:
     ```sql
     SELECT file_id, name, error FROM unlim_files WHERE status = 'skipped';
     ```
5. **Измерение скорости (`SpeedMeter`) и интеграция с Web UI:**
   * Встроенный класс `SpeedMeter` рассчитывает мгновенную скорость (скользящее окно 3 сек) и среднюю скорость сессии в **МБ/с** и **Мбит/с**.
   * Статус транслируется в `logs/download_status.json`, откуда считывается веб-дашбордом `webui.py` (`/api/status`) и отображается в виде бейджа `⚡ Скорость` в шапке дашборда.
6. **Параметры запуска и ускорения:**
   * `--from-end`: Скачивание с конца очереди (`rowid DESC`), что позволяет в первую очередь забирать стабильные файлы старых архивов.
   * `--timeout 7`: Ограничение времени ожидания (3 сек connect + 7 сек read), мгновенно отсекающее зависшие ноды Яндекса без задержки пула потоков.
   * `--workers 10`: Ориентир для мощных машин. На машинах с малым ОЗУ используйте `auto_workers()` (на 5,9 ГБ ОЗУ — 3 потока) или `--workers 3`.
   * **Дедлайн на файл:** `max(120, timeout * 60)` секунд — защита от «сочащихся» мёртвых шардов (см. §12).

## 11. Октябрь 2026: Стабилизация скачивания обычного диска и сетевая оптимизация

В ходе натурного тестирования скачивания обычного диска (REST API) был выявлен и полностью устранён ряд скрытых архитектурных и сетевых проблем:

### 1. Исправление сортировки очереди в `state.py` (Устранение бага «скачивается фигня»)
* **Причина:** Исходный метод `get_pending()` выполнял выборку:
  ```sql
  SELECT remote_path, size, md5 FROM files WHERE status='pending' ORDER BY size ASC
  ```
  При наличии на Диске пользовательских папок с кэшами программ (например, Telegram, Web-клиенты в `Загрузки/...`) с тысячами микро-файлов по 50–200 байт (`section_sessions.png`, `media_video.png`, `project_id.ini`), скрипт выстраивал очередь из сотен микро-иконок. На локальном диске создавалось глубокое дерево папок со служебными иконками, создавая впечатление поломки.
* **Решение:** Метод обновлён до `get_pending(order_by="rowid ASC")`. Теперь файлы скачиваются в естественном порядке обхода дерева (корневые фотографии, документы, пользовательские папки), либо по настраиваемому параметру.

### 2. Устранение сетевых зависаний (Path MTU Blackhole & IPv6 Stalls)
* **Проблема MTU:** Сетевые интерфейсы виртуализации (Linux VirtualBox) и туннели (NAT/VPN/PPPoE) используют MTU 1500, однако пакеты с полезной нагрузкой более 1420 байт (MTU > 1448) молча сбрасывались промежуточными шлюзами без отправки ICMP Fragmentation Needed. Это приводило к зависанию TCP-соединений при получении первых же пакетов с данными от CDN Яндекса (`s393klg`, `s447klg` и др.) и ошибкам `ReadTimeoutError`.
* **Проблема IPv6:** DNS-запросы возвращали IPv6-адреса серверов хранения (`2a02:6b8:...`), к которым соединение не проходило (`[Errno 111] Connection refused`), увеличивая задержки при поочерёдном переборе адресов.
* **Решение:** В модуль [`downloader.py`](downloader.py) встроен низкоуровневый хук `urllib3.util.connection`:
  * Принудительно отключён IPv6: `allowed_gai_family = lambda: socket.AF_INET`.
  * Принудительно ограничен размер TCP-сегмента: `socket.setsockopt(socket.IPPROTO_TCP, socket.TCP_MAXSEG, 1360)`. Это гарантирует прохождение пакетов через любые типы туннелей и NAT без фрагментации.

### 3. Обработка повреждённых реплик Яндекса (`file IO failure`) и оптимизация повторов
* **Сбойные реплики:** На стороне серверов Яндекса отдельные файлы возвращают HTTP 500 с телом `file IO failure: no more reliable hosts` (физическая утеря блоков данных в кластере Яндекса).
* **Политика повторов:** В `downloader.py` внутренние повторы `yadisk` отключены (`n_retries=0`), чтобы битые файлы не занимали поток на минуты. Скрипт фиксирует статус `failed`, сохраняет текст ошибки и немедленно приступает к следующему файлу. Повторный проход — только осознанно, командой `main.py retry-failed`.
* **Таймауты:** В вызовы `client.download()` переданы явные таймауты соединения и чтения `timeout=(10.0, 10.0)` взамен стандартных значений библиотеки `yadisk`.
* **Особенность Windows:** `TCP_MAXSEG` на Windows не поддерживается (`WinError 10042`), поэтому в коде есть проверка `_TCP_MAXSEG_SUPPORTED` — clamp MSS применяется только там, где ОС это умеет; принудительный IPv4 работает на всех платформах.

### 4. Автоматический подъем Веб-Дашборда
* Точка входа [`main.py`](main.py) обновлена: при вызове без параметров (например, двойной клик или `python main.py`) скрипт автоматически определяет наличие `webui.py` и запускает единую графическую панель на `http://localhost:8000`.
* В веб-интерфейсе реализован прямой вызов системного диалога выбора папок ОС (`kdialog` / `zenity` / `tkinter` / Windows Explorer), что позволяет визуально указывать директории выгрузки без ручного ввода путей.

## 12. Октябрь 2026: Пожары в хранилищах Яндекса и текущая эксплуатация

### 12.1. Что случилось

Часть серверов хранения Яндекса (`*.storage.yandex.net`) была физически утрачена. Последствия для выгрузки:

* файлы на мёртвых шардах стабильно возвращают `HTTP 500 InternalServerError` или `file IO failure: no more reliable hosts`;
* часть нод отвечает `Read timed out` / `IncompleteRead`;
* третий, самый неприятный режим — **«сочащиеся» шарды**: TCP-соединение живёт, байты приходят реже, чем срабатывает read-таймаут, поэтому `iter_content` не рвётся и поток зависает надолго.

### 12.2. Внесённые исправления

1. **Дедлайн на файл в `unlim_backup.py`.** В `download_one_file` добавлен общий лимит `max(120, timeout * 60)` секунд (~420 с при `--timeout 7`). При превышении файл помечается `skipped` с причиной, поток освобождается. Это устранило вечные зависания пула на «сочащихся» нодах.
2. **Автоподбор числа потоков (`utils.auto_workers()`).** Число потоков по умолчанию зависит от ОЗУ: ≤4 ГБ → 1, ≤6 ГБ → 3, иначе 4. Явный `--workers` переопределяет значение. На машине с 5,9 ГБ ОЗУ `auto_workers()` даёт 3 потока.
3. **Проверка свободного места (`downloader.check_free_space`).** Перед каждым файлом требуется `size + 50 МБ`. При нехватке файл получает результат `disk_full`, загрузка останавливается, неначатые файлы остаются `pending`.
4. **Переезд выгрузки на другой диск.** Диск `D:` заполнился (свободно ~5,8 ГБ из 931,5 ГБ), поэтому `.env` переключён на `C:\NeUnlim` (диск) и `C:\Unlim` (безлимит). Для `unlim_backup.py` путь задаётся явно: `--out-dir "C:/Unlim"` (значение по умолчанию в скрипте — Linux-путь `/media/vb/backup Ya1/Unlim`).
5. **Сторожевой контроль.** Внешний сторож следит за свободным местом на `C:` с порогом 50 ГБ: при падении ниже порога загрузчики останавливаются, чтобы не забить системный диск. Дополнительно `memcheck.py` отдаёт объём свободной ОЗУ для сторожевых проверок.

### 12.3. Правила эксплуатации

* **Остаток очереди — это в основном мёртвые шарды.** Повторные прогоны имеют смысл только после восстановления серверов Яндексом; ожидаемый прирост — единицы-десятки файлов за ночь.
* **Не сбрасывайте `failed → pending` массово** без явной просьбы: мёртвые файлы возвращаются в очередь и замедляют полезную выгрузку. Штатный путь — команда `python main.py retry-failed`, которая сама сбрасывает `failed` и сразу качает.
* **Не удаляйте базы** `state.db` / `unlim_state.db` — это реестр уже скачанного.
* **Не усекайте `logs/unlim_backup.log`** (бывает сотни МБ) без согласия владельца.
* **Не выводите** содержимое `.env` (`YA_DISK_TOKEN`) и `cookies.json` в чат, логи и документацию.

### 12.4. Команды для продолжения

```bash
# обычный диск: failed → pending → скачивание
python main.py retry-failed --workers 4

# безлимит: сначала pending, затем один проход skipped
python unlim_backup.py --target all --media all --out-dir "C:/Unlim" --workers 4

# отчёт по недоступным файлам
python report_status.py   # → logs/download_report.md
```




## 13. Октябрь 2026: «Скачать всё» как полный цикл (v35.5.1)

Кнопка **«Скачать всё»** больше не запускает только два скачивания: теперь это
оркестратор `webui.FullCycle` (синглтон `webui.full_cycle`, эндпоинт
`POST /api/download/all`, поля `workers`, `passes`, `sort_after`).

Две полосы выполняются параллельно, у каждой свои задачи в `TaskManager`:

| Полоса | Шаги |
|---|---|
| Диск | `main.py scan` → `main.py download --workers N --no-scan --retry` → повтор проходов |
| Безлимит | `unlim_download.py --collect` → `unlim_backup.py --target all --media all` → повтор проходов (опционально `organize.py`) |

Проходы по сбойным: ровно `passes` (1–10, по умолчанию 3), пауза 60 секунд.
Досрочной остановки нет: отсутствие прогресса только пишется в журнал
(`FullCycle._progress_note()`). Ошибки Диска — статус `failed`, Безлимита —
`skipped`. Счётчики берутся из `state.db` / `unlim_state.db` через
`FullCycle._db_snapshot()`: разница «скачано» даёт результат прохода, текущее
число сбойных — остаток. Если проход не уменьшил число сбойных, дальнейшие
проходы не запускаются.

По завершении `full_cycle.summary` отдаётся в `/api/status`, UI показывает
модальное окно «Скачивание завершено» и оставляет те же строки в карточке
процесса. Код возврата 1 от `main.py` (часть файлов не скачалась) больше не
считается остановкой: интерфейс пишет «Завершено с ошибками (N файлов)» и
показывает число ошибок в бейджах сессии.

Старый оркестратор `AutoRuns` и галочка «Сначала новые, затем сбойные» удалены:
повтор сбойных теперь всегда входит в полный цикл, а прогон только новых файлов
остаётся в пошаговом режиме.

## 15. Октябрь 2026: установка без прав администратора (v35.5.3)

Раньше установщик ставил программу в `Program Files` и требовал UAC — значит,
и установка, и каждое самообновление показывали запрос администратора. Для
домашней машины это лишнее: все данные и так лежат в `%LOCALAPPDATA%`.

**Установщик** (`installer/yadisk_backup.iss`):

- `PrivilegesRequired=lowest`, `DefaultDirName={localappdata}\Programs\YandexDiskBackup`;
- `ArchitecturesInstallIn64BitMode` убран — 64-битный режим установки доступен
  только с правами администратора;
- ярлыки — `{userprograms}` и `{userdesktop}`, автозапуск — ветка `HKCU`;
- `LegacyInstallDir()` в `[Code]` читает `InstallLocation` из ключа удаления
  `{8E4A3F42-…}_is1` в HKLM (обе ветки реестра). Если найдена прежняя
  system-wide установка, `InitializeSetup` спрашивает, продолжать ли, и
  напоминает удалить старую копию через «Параметры → Приложения». В тихом
  режиме (самообновление) вопрос подавляется и установка идёт дальше.

**Определение типа сборки** (`webui.py`):

- `_read_install_locations()` читает `InstallLocation` всех записей из реестра удаления
  (HKCU/HKLM, 32 и 64 бита), кэш 60 секунд — `/api/status` опрашивается
  каждые 1.5 сек;
- `UpdateManager.is_portable()` сначала сверяет папку из реестра с папкой exe:
  совпала — это установка (обновляем `setup.exe`), не совпала — распакованный
  ZIP. Раньше признаком portable было «вне Program Files», и пер-пользовательская
  установка в `%LOCALAPPDATA%\Programs` обновилась бы ZIP-ом;
- `legacy_install_dir()` / `legacy_install_status()` — путь старой копии в
  Program Files для баннера; ключ `legacy_install` в `/api/status`;
- в интерфейсе добавлен баннер `#legacy-install-banner` с путём старой папки и
  инструкцией по удалению. Он исчезает, когда запись в реестре пропадает.

**Помощник установки** (`write_update_helper`) для `setup` больше не запускает
прежний путь: после установки он берёт `InstallLocation` из HKCU и открывает
именно новую копию. Иначе обновление из `Program Files` перезапускало старый exe.

**Миграция.** Автоматически перенести установку из `Program Files` нельзя без
прав администратора, поэтому старая копия снимается один раз вручную. Данные,
базы, `.env`, куки и скачанные файлы лежат в `%LOCALAPPDATA%\YandexDiskBackup`
и при удалении не затрагиваются. Обновлятор, запущенный из старой копии,
предложит перейти на новый установщик.

## 17. Октябрь 2026: починка запуска самообновления (v35.5.5)

Симптом: «Диагностика» → «Обновления» → «Обновить» скачивал установщик
(полоса доходила до конца), «Перезапустить и установить» спрашивал
подтверждение, программа закрывалась — и всё. Версия оставалась прежней,
`%TEMP%\YandexDiskBackup_update\install_update.log` не появлялся,
лог Inno Setup не создавался.

Причина в `api_updates_install` (`webui.py`): помощник запускался с
`creationflags = DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`. С
`DETACHED_PROCESS` процесс `powershell.exe` создаётся без консоли, сразу
завершается с кодом 0 и **не выполняет** переданный `-File`. `subprocess.Popen`
при этом возвращает успех, поэтому программа спокойно закрывалась, а установщик
не запускался ни разу. Проверено на Windows 10 перебором флагов:
`DETACHED_PROCESS` — скрипт не выполняется; `CREATE_NO_WINDOW`,
`CREATE_NEW_PROCESS_GROUP` и их комбинация — выполняется и переживает выход
родителя.

Что изменено:

- флаги запуска — `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`;
- помощник первой строкой пишет в `install_update.log` «помощник запущен …»,
  затем код установщика. Пустой лог = PowerShell не запустился;
- при ненулевом коде установщика помощник показывает окно
  `[System.Windows.MessageBox]` с кодом ошибки, а не молчит;
- регрессионный тест `test_update_helper_is_not_started_detached` и проверки
  содержимого скрипта-помощника в `tests/test_webui.py`.

**Переход.** Сломан запуск был и в 35.5.3, и в 35.5.4 (код тот же), поэтому
35.5.5 ставится один раз вручную запуском `setup.exe`. Дальше обновление из
приложения работает: 35.5.5 запускает помощника уже исправно.

## 19. Октябрь 2026: сессионные счётчики и правки интерфейса (v35.5.7)

**Кодировка вывода дочерних процессов.** В установленной сборке stdout —
консольная кодировка Windows (cp1251). `main.py` печатал `→` при обходе корней,
падал с `UnicodeEncodeError` и обрывал сканирование: линия Диска оставалась без
единого файла, а полный цикл висел до ручной остановки. В начале `main.py`
теперь `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` — так же, как
в остальных скриптах.

**Завершение задач.** `Task` получил флаг `finished`: поток чтения ставит его
после EOF в stdout и `proc.wait()`. `Task.alive()` учитывает флаг, поэтому задача,
закрывшая вывод, больше не считается живой, даже если `poll()` ещё отдаёт `None`.
`FullCycle._wait_task` ждёт код возврата до 5 секунд и иначе возвращает 1.

**Сессионные счётчики.** `webui.reset_session_counters(kind)` удаляет
`logs/download_status.json` или `logs/disk_download_status.json` перед стартом
задачи (`/api/download/start`, линии полного цикла). Писатели статуса
(`downloader._write_disk_status`, `unlim_direct.update_status_file`) добавляют
`started_at` — момент старта своего процесса. В интерфейсе `statusIsFresh()`
сравнивает `updated_at` со `started_at` (или с временем работы задачи), и пока
свежего статуса нет, плашки показывают «⏳ подготовка», а не числа прошлой сессии.
Дублирующие зелёные бейджи из панели управления удалены вместе с `live-speed-badge`.

**Уникальный счёт пропущенных.** `unlim_backup.py` считает skipped по множеству
`file_id` (и снимает id при успехе во второй фазе): раньше фаза 2 повторяла те же
файлы и счётчик удваивался.

**Служебные плашки.** Токен, куки и сторож помечены классом `pill.service`,
отделённые `.pills-sep`; включённый сторож — `.pill.info` (синий). Определения
состояний: `.badge.warn` (оранжевый, частичный сбой) и `.badge.stop`
(нейтральный, остановлено пользователем).

**Прочее по интерфейсу.** Кнопка «Показать» у токена меняет подпись на «Скрыть»,
неактивна при пустом поле (`syncTokenViewButton()`) и возвращает скрытый вид при
очистке. Порог сторожа применяется на лету (`applyWatchdogThreshold()` +
`DiskWatchdog.start` обновляет `threshold_gb` у работающего сторожа). Кнопки
«Сброс очереди» неактивны, когда счётчик нулевой или идёт выгрузка. Нижние
карточки «Главной» занимают всю ширину (`.panel[data-panel="home"] > .card`),
поэтому на широком экране справа нет пустой половины. Удалены девять мёртвых
JS-функций, тосты и подсказки приведены к «вы».

## 20. Октябрь 2026: база Безлимита и недоступная папка выгрузки (v35.5.8)

**«Пересоздать базу» ломала базу Безлимита.** `populate_db_from_cloud(force=True)`
удалял таблицы `unlim_files` и `unlim_clusters`, но `PRAGMA user_version`
оставалась равной 1. `db_migrations.migrate()` считал миграцию №1 применённой,
`CREATE TABLE IF NOT EXISTS` не выполнялся — и любой следующий запуск падал с
`sqlite3.OperationalError: no such table: unlim_clusters` (и в сборе списка, и в
скачивании). Теперь вместе с таблицами сбрасывается версия схемы
(`db_migrations.set_user_version(con, 0)`), а в `unlim_schema.MIGRATIONS` добавлена
миграция №2: она повторно применяет `DB_SCHEMA` и тем самым лечит базы, уже
испорченные версией 35.5.7. Схема идемпотентна, повторный запуск безопасен.

**Недоступная папка выгрузки.** Если папка лежит на отключённом диске (внешний
HDD, флешка, сетевой ресурс), `os.makedirs` бросает `FileNotFoundError [WinError 3]
«Системе не удаётся найти указанный путь: 'G:\'»`. Исключение всплывало в потоке
скачивания и в диспетчере задач (`webui.dispatch_worker`), и пользователь видел
окно «Unhandled exception in script» с трейсбеком. Введена `utils.check_target_dir()`
— она возвращает причину по-русски или `None`. Проверка стоит:

* в `webui.api_download_start` (обе моды) — отказ с сообщением, задача не стартует;
* в линиях полного цикла (`_disk_lane`, `_unlim_lane`) — линия уходит в ошибку;
* в `downloader.download_all` — `SystemExit(2)` с текстом в stderr;
* в `unlim_backup.main` — выход с сообщением до открытия базы.

Если диск отключится посреди прохода, `downloader._download_one` ловит `OSError`
при создании подпапки и возвращает `DownloadResult(status="failed", error="Не
удалось создать папку: …")` — остальные файлы продолжают качаться.

**Ошибки фоновых задач без системного окна.** `launcher.main` оборачивает

## 21. Октябрь 2026: итоги сессии, кликабельные плашки, таймер (v35.5.9)

**Счётчики плашек копятся за сессию.** Итог жил на уровне одного вызова
`download_all()`: `main.py download --retry` после первого прохода делал
`reset_failed_to_pending()` и вызывал `download_all()` второй раз — счётчики
начинались с нуля и перезаписывали файл статуса. Теперь `download_all(session=…)`
принимает накопленные значения, а пустой проход пишет их же, а не нули. В полном
цикле файл статуса по-прежнему обнуляется перед каждым проходом (он описывает
один процесс), но итог линий (`lane["downloaded"]`) копится за все проходы.

**Блок `session` в `/api/status`.** `webui.build_session()` — чистая функция,
принимает статус полного цикла, задачи, оба файла статуса и счётчики баз. Возвращает
по разделу: `success` (скачано за сессию), `failed` (сколько файлов сейчас сбойные
в базе — каждый файл один раз), `remaining` (сколько ещё предстоит: `pending` плюс
сбойные, если сессия их повторяет), `running`, `preparing`, `pass`, `passes`.
Владелец сессии — идущий полный цикл; после его завершения линия остаётся
владельцем, пока не запустят отдельную выгрузку (её `started_at` позже
`finished_at` цикла). Пока дочерний процесс прохода жив, к итогу линии
прибавляются его живые цифры. UI только рисует: `renderSessionPill()`.

**Ранний нулевой статус.** `downloader.write_status_start()` и
`unlim_backup.run_backup()` пишут нули с `active=True` до проверки токена/куки и
сборки списка, поэтому «⏳ подготовка» больше не висит на сетевых запросах.
У `unlim_backup.update_status_file()` появился `started_at`.

**Кликабельные плашки.** `showPanel(name)` заменил анонимный обработчик табов,
`revealTarget(panel, selector)` прокручивает к полю, подсвечивает карточку классом
`.flash` и ставит фокус, `gotoSetting()` объединяет оба. Карта `PILL_TARGETS`
связывает плашки шапки с настройками; у плашек есть `role="button"`,
`tabindex="0"` и обработка Enter/Space. Подсказки `data-tip` не перехватывают клик
(`pointer-events:none`).

**Таймер до конца.** `etaFor()` считает среднюю скорость процесса по файлу статуса
(попытки / время работы) и делит на неё `remaining`; `renderEta()` пишет «⏳ Осталось
примерно» в `#eta-box` карточки «Выполнение процесса». Первые 30 секунд прохода
оценка не показывается, при двух линиях — две цифры.

**Прочие исправления.** Полный цикл проверяет код возврата прохода (`code not in
(0, 1)` — ошибка линии) и поле `error` в статусе Безлимита (`cookies_expired`,
`disk_full`), а не молча пишет «готово». Отмена обновления кук (`cancelled`,
`stopped`) рисуется нейтрально. Кнопка «Обновить» исчезает после скачивания
установщика — остаётся только «Перезапустить и установить».

## 22. Октябрь 2026: отчёты для разбора сбоев, мониторинг, базы (v35.6.0)

**Зачем.** Отчёт из «Диагностики» был слишком бедным для удалённого разбора: по
нему нельзя было понять, какой сервер Яндекса отвечает ошибкой и одинаковы ли
сбои. Первый внешний пользователь как раз прислал скриншоты вместо отчёта —
теперь такой нужды нет.

**Группы сбоев.** `diagnostics.failure_groups(path, table, path_col)` читает
сбойные строки базы, склеивает тексты по сигнатуре (`_signature()` убирает
номера запросов и числа) и хосту (`error_host()`, `HOST_RE` понимает и полный
URL, и `HTTPSConnectionPool(host='…')`), суммирует количество и размер, берёт до
10 примеров путей по исходным текстам группы. В отчёте — до 12 групп,
`groups_total` — сколько их всего.

**Тело и заголовки ответа.** `downloader.record_http_error()` складывает в
`logs/http_errors.json` (до 25 записей) статус, `Retry-After`, `X-Request-Id`,
`X-Yandex-Req-Id`, `Server` и первые 1 КБ тела. Запись атомарная и никогда не
бросает — сетевой сбой не должен ломать скачивание. В отчёте —
`http_errors` со счётчиками по статусам.

**История попыток.** У таблицы `files` появилась колонка `attempts` (миграция
№2, `mark_failed` увеличивает счётчик). `database_info()` отдаёт распределение
`0-1 / 2-3 / 4-9 / 10+`, `quick_check`, режим журнала и число дублей по имени.

**Сравнение отчётов.** `report_delta()` читает `report.json` последнего ZIP в
`reports/` и сравнивает счётчики: `{was, now, delta}` по каждому полю. Первый
отчёт отвечает `{"available": false}`.

**Логи в архиве.** `write_report()` кладёт в `logs/` хвосты (до 2 МБ и 20000
строк) десяти логов, включая `crash.log`; секреты проходят `redact_text()`.

**Хук исключений.** `diagnostics.install_crash_hook()` ставит `sys.excepthook` и
`threading.excepthook`: трейсбек после редактирования пишется в
`logs/crash.log` (файл обрезается по 512 КБ), затем один раз за процесс
отправляется автоотчёт, если ключ настроен. Вызывается из
`webui.start_background_services()` — общей точки для `webui.main()` и
`launcher.py`.

**Мониторинг.** `monitor.py`: поток раз в 15 минут отправляет
`POST /heartbeat` (версия, `phase`, счётчики Диска и Безлимита, свободное
место — без путей и имён). `evaluate()` — чистая функция порогов: сбои ≥ 25
файлов и ≥ 25 %, свободно < 2 ГБ, истёкшие куки, код возврата задачи ∉ {0, 1}.
Дедуп — один час на ключ, состояние в `DATA_DIR/.monitor_state.json`.
`start_monitor()` не стартует без ключа отправки; ошибки сети не выходят наружу.
В `/api/status` добавлен блок `monitor`.

**Worker.** `POST /heartbeat` принимает до 64 КБ JSON, кладёт запись в KV
`HEARTBEATS` (TTL 30 дней) и пересылает алерты в Telegram; `GET /summary`
отдаёт список установок, активных за сутки, и общие счётчики. Без привязки KV
heartbeat работает, `/summary` отвечает `501`. Привязка описана в
`worker/wrangler.toml` и `worker/README.md`.

**Базы.** Один блок `/api/db/*` для обеих баз (`DB_TABLES = {disk, unlim}`):
`rebuild` — копия через sqlite backup API → `State.reset()`/`--force` → пересборка;
`relocate` — `UPDATE local_path` относительно новой папки без скачивания;
`redownload` — копия, очередь в `pending`, новая папка в `.env`, старт выгрузки.
Для Диска добавлен флаг `main.py scan --force`. Старый `/api/unlim/rebuild`
делегирует в общий обработчик.

**Интерфейс.** Общий таймер считает максимум по линиям (`etaSeconds()`), детали
по каждой — в подсказке. Плашка сторожа — тот же овал без заливки и рамки
(`.pill.service.on`). Порядок карточек: папка Безлимита → сторож → токен.
Свёрнутые инструкции показывают шеврон и «развернуть», автораскрываются, если
не настроены. `makeResizable()` даёт ручку на нижнюю грань и уголок ширины,
размер хранится в `localStorage`, двойной клик сбрасывает. Мастер первого
запуска принимает куки и умеет «Обзор…» для папок.

## 23. Октябрь 2026: проходы по числу, а не по прогрессу (v35.6.1)

**Проблема.** `FullCycle` считал прогрессом только уменьшение числа сбойных в
базе и при `after >= before` выходил из цикла («прогресса нет — проходы
прекращены»). В сессии 29 октября Диск скачал 21 файл (21 OK и 800 FAIL с HTTP
500), у Безлимита пропущенных стало 856 → 808, но сбойные остались на уровне

`#all-runs max="10"`).

## 24. Октябрь 2026: сбор базы Безлимита без зависания, остаток очереди, таймер по успехам (v35.6.2)

**Зависание сбора базы (первый тестер, 35.5.9).** В журнале —
`[Кластеры: 1052403/3197 (32914%)]`, процесс шёл 5 ч 29 мин, «Безлимит:
подготовка…» не заканчивалась. Причина: цикл в `populate_db_from_cloud`
помечал `fetched=1` только те кластеры, которые сервер вернул в ответе. Если
Яндекс не отдавал кластер (пустой/удалённый), он навсегда оставался
`fetched=0`, и цикл запрашивал те же 16 кластеров заново.

**Решение.** `missing_tries` считает неудачные попытки по каждому кластеру;
после `MISSING_TRIES = 3` кластер помечается обработанным и попадает в журнал
(«Сервер не отдал N кластер(ов)… — пропущены»). Процент прогресса ограничен
100. Заодно `unlim_files` при повторном сканировании дозаполняет `size`/`md5`
у уже известных файлов (`ON CONFLICT DO UPDATE` только для пустых полей,
статус не меняется) — без этого у 808 пропущенных размер оставался нулевым.

**Остаток очереди и плашки.** `db_stats()` отдаёт `bytes_by_status`, а
`build_session()` — `remaining_bytes` (pending + сбойные, если сессия их
повторяет). Плашки `#pill-disk-session` и `#pill-session` больше не скрываются
без сессии: в покое показывают «⚠ 400 · 52 ГБ» (сколько осталось докачать),
во время работы — прежний итог, остаток — в подсказке.

**Таймер.** Старая формула делила остаток на «все попытки / всё время», и
`failed` из файла статуса (число попыток, 800 против 400 файлов) выдавался за
сделанную работу: получалось «~1 мин» при нуле скачанного. Теперь UI держит
замеры за 3 минуты (`ETA_WINDOW = 180`) и считает скорость только по успехам;
для Диска — по `bytes` и `remaining_bytes`, для Безлимита — по файлам. Первые
`ETA_MIN_ELAPSED = 120` секунд, при нуле успехов за окно и при статусе старше
2 минут цифры нет. Счётчики сбросились (новый проход) — окно начинается заново.

**Журнал и отчёт.** Перед повторной попыткой в журнал пишется «сброшено в
очередь: N сбойных файлов» (Диск) и «в повтор пойдут: N пропущенных файлов»
(Безлимит). Результат отправки отчёта сворачивается в строку
`.list-toggle` («✅ Отчёт отправлен · 1,2 МБ»), список отчётов — тоже
сворачиваемый; после сборки отчёт раскрыт для чтения.

## 25. Октябрь 2026: внешний диск и «молчащие» серверы (v35.6.3)

**Зачем.** Первый тестер работает на внешнем диске `G:` и видел два разных беды
как одну: «451 сбойный файл». На самом деле часть файлов не отдавали серверы
Яндекса (их надо просто дождаться), часть падала с `WinError 3`, когда диск
отключали, а сообщения были одинаковыми и не подсказывали, что делать.

### A1/A2 — путь и проверка папки

Под полем пути — подсказка «полный путь с буквой диска, например `G:\Бэкап`».
Относительный путь не блокируется: `saveDiskDir()`/`saveUnlimDir()`/`finishSetup()`
показывают мягкое предупреждение (`toast(..., 'warn')`), `_looksAbsolute()`
распознаёт `X:\`, `\server` и `/`.

`utils.check_target_path()` проверяет папку, ничего не создавая: буква диска
(если корня `G:\` нет — «Диска G: сейчас нет»), ближайший существующий родитель,
права на запись, свободное место; возвращает готовую фразу для интерфейса.
Роут — `POST /api/check_dir` (`DirCheckPayload`), кнопка «Проверить папку» —
`checkFolder(inputId, statusId)`.

### A3 — куда скачиваем

`download_all()` и `run_backup()` печатают первой строкой
`Скачиваем в: <абсолютный путь>` — до проверки токена и сбора списка.

### B0 — типизация локальных ошибок

`utils.classify_local_error()` делит `OSError`: `WinError 123/206/225`,
`ENAMETOOLONG`, `EINVAL`, `EILSEQ` → `local_file` (виновато имя файла);
`WinError 112`, `ENOSPC` → `disk_full`; остальное → `local_disk`.
`DownloadResult.is_local_error` истинно для `failed` с `local_disk|local_file`.
`download_all()` считает такие ошибки подряд: `LOCAL_ERROR_LIMIT = 8` останавливает
проход (`stop_state="disk_offline"`, `pool.shutdown(cancel_futures=True)`),
файлы остаются в очереди, попытки не тратятся. Успешный файл сбрасывает счётчик.
UI показывает плашку `#disk-offline-banner` по `disk_state` из `/api/status`.

### B1 — `fetch.py`

Своя загрузка вместо `client.download()`: `get_download_link()` → цикл до 5 хопов
с `allow_redirects=False` → `urljoin`, поэтому известен host сервера хранения.
`DeadHosts` (TTL `30*60` с, `threading.Lock`, `clock=time.monotonic`) хранит
молчащие серверы: `is_dead(host)` → `storage_skip` без запроса. OAuth-токен
уходит только на первом запросе (он в заголовке ссылки от API), на хранилище —
обычный GET. Поток 1 МиБ, MD5 и размер считаются на лету; запись в
`.yadisk-<hex>.part` → `os.replace` (старый файл не удаляется заранее — при
сбое остаётся предыдущая копия). `FetchFailure` типизирован:
`storage_down/storage_skip/server_50x/rate_limit/timeout/connection` (отложить),
`not_found/refused/bad_file/local_*` (сбой или локальная проблема).
`scrub_urls()` вычищает подписанные ссылки из текстов ошибок и логов.

### B2 — «ждут Яндекса»

`state.mark_deferred(remote_path, kind, host)` оставляет файл `pending` с
маркером `error = "storage_down | <host>"`, пишет `storage_host`, `attempts`
не трогает; `is_deferred_error()` и `deferred_marker()` — общий формат с
`unlim_backup`. `get_pending(deferred_first=True)` ставит отложенные вперёд.
`get_stats()`/`db_stats()` отдают `waiting`. В UI — плашка `#waiting-banner`
(счётчик `waitingTotal(s)` по обеим базам) и кнопка «Попробовать сейчас»
(`retryWaiting()` → `/api/download/start`). В конце прохода журнал пишет
«Из N ждавших Яндекса скачано M».

У Безлимита `take_batch()` увеличивает `attempts` при выдаче пачки, поэтому
`mark_deferred()` откатывает её (`attempts - 1`) и обнуляет `assigned_at`.
Результаты с `storage_down`/`storage_skip` не считаются `skipped` — иначе
отложенные файлы возвращались бы в очередь как сбойные.

### B3 — превью отложенных фото

`previews.py`: `preview_path_for()` кладёт копию в `<папка>/_превью/<путь>.jpg`;
`make_disk_preview()` пробует `client.get_meta(preview_size=X)` для
`XXXL → XXL → XL`; у Безлимита `unlim_preview_url()` делает POST
`models-v2?m=mpfs/info` с `requestParams: {path, meta: "sizes"}` и берёт
`XXXL/XXL/XL` из `meta.sizes`. Запись атомарная (`fetch_to_file`), путь
хранится в `preview_path` (миграции `state.py` №3–4, `unlim_schema.py` №3).
`sweep()` при старте удаляет превью у скачанных/пропущенных файлов, забывает
пути пропавших и чистит брошенные `.part` старше суток. Настройка
`PREVIEWS` (по умолчанию включена), роут `POST /api/config/previews`,
у Безлимита `--no-previews`.

## 27. Октябрь 2026: Безлимит не крутит отложенные файлы по кругу (v35.6.5)

Живой прогон 35.6.4 показал: Диск откачал всё, что отдаётся (21 105 из 21 505,
остальные 400 ждут Яндекса), а Безлимит висел на «проходе 1 из 10» больше пяти
часов — батч #388…#402 по 780 файлов, в каждом «Успешно: 0/780».

Причина: `mark_deferred()` возвращает файл в `pending` с откатанным `attempts`,
`take_batch()` сортирует `attempts ASC`, поэтому тот же файл снова оказывался
первым, а `run_backup()` выходил из цикла только когда `take_batch()` вернул
пусто. Пока серверы Яндекса молчат, пусто не станет никогда.

Что сделано:

* `take_batch()` сортирует отложенные (`error LIKE 'storage_down%'`) в конец
  очереди — новые файлы всегда впереди. Это важно и для стоп-условия: батч,
  целиком состоящий из отложенных, теперь означает, что других файлов нет.
* `run_backup()` завершает проход, если в батче `0 скачано и 0 сбойных`
  (весь батч отложен). Перед этим, как и раньше, делается одна попытка повтора
  пропущенных (`reset_skipped_files`), если очередь была `all`.
* Счётчик отложенных считается по уникальным `file_id` (`deferred_ids`): раньше
  каждая повторная попытка прибавляла единицу, и статус показывал «319 465 ждут
  Яндекса» при 187 файлах в базе.
* `downloader.download_all()`: `waiting_count` из `_waiting_stats(state)` уже
  содержит отложенные файлы прохода, поэтому прибавляется только файл, который
  ждал не раньше (`not res.job.was_deferred`) — вместо «ещё ждут: 800» при 400
  файлах.

`test_run_backup_finishes_pass_when_everything_waits_for_yandex`,
`test_waiting_counter_is_not_doubled` (всего 411).

Четвёртый отчёт тестера (30.10, уже 35.6.7) показал, что порог из десяти 5xx —
тоже ошибка. Проход Диска 00:01:23–00:12:20: `00:01:26–00:01:31` — десять

500 идут по папкам («Чупсик», «Тони», «Серёжа наш сыночек!», «Сергиев Посад»),
поэтому порог набирается за шесть секунд. В ручном режиме «только Безлимит» с
того же `downloader.disk.yandex.ru` в это же время качалось 7,6 МБ/с и 51 файл
из 57 — сервер жив.

Что сделано:

* **`fetch.DeadHosts` больше не гасит хост по ответам 5xx.** Удалены
  `note_reply_error()`, `note_ok()`, `error_count()` и `SERVER_ERROR_LIMIT`.
  `mark()` остаётся только для сетевых ошибок (`timeout`, `connection`,

  экономить нечего, а цена ошибки — целый проход.

  `server_fails`, после трёх проходов — `lost`).
* **Красные кнопки «Стоп».** `.big-btn.danger` не задавал цвет текста, а
  `button.danger` (специфичность 0,1,1) перебивал белый `.big-btn` (0,1,0) —
  получался красный текст на красном фоне. Добавлено `color:#fff`.
* **Уведомления через трей.** В WebView2 `Notification.permission` всегда
  `denied`, и `requestPermission()` не спрашивает пользователя, поэтому карточка
  «🔔 Уведомления о завершении» из 35.6.4 не могла включиться ни у кого.

  прежний браузерный путь, а кнопка честно пишет «недоступны».
* **Оценка очереди и места.** `#queue-estimate` под плашкой ожидания:

## 33. Октябрь 2026: профили клиентов и окно «Что нового» (v35.7.1)

Две крупные вещи по просьбе Сергея: обслуживать чужие облака с одной машины,
не смешивая данные, и видеть перед обновлением, что изменилось в новой версии.

### Профили пользователей

* **Идея.** Все изменяемые данные программы уже собраны в одном каталоге
  (`paths.DATA_DIR`), а переменная `YADISK_DATA_DIR` переопределяет его ещё до
  импорта модулей. Профиль — это отдельный каталог данных, поэтому
  «сменить пользователя» = перезапустить программу с другим `YADISK_DATA_DIR`.
  Внутри процесса пути поменять нельзя: они вычисляются при импорте `paths`.
* **`paths.py`.** Добавлен `BASE_DATA_DIR = _default_data_dir()` — «родной»
  каталог данных, не зависящий от `YADISK_DATA_DIR`. В нём живёт реестр
  профилей, и он же является профилем «Основной».
* **`profiles.py`.** Реестр `BASE_DATA_DIR/profiles.json` со списком
  `[{id, name, dir, created}]`; папки профилей — `BASE_DATA_DIR/profiles/<id>/`.
  API: `list_profiles()`, `current_profile()`, `create_profile()`,
  `rename_profile()`, `delete_profile()`, `profile_dir()`, `validate_name()`.
  Битая JSON-запись реестра не ломает окно — читаем как пустой список.
  Основной профиль не переименовывается и не удаляется; удалить активный
  профиль или папку вне `profiles/` тоже нельзя (`delete_profile()`;
  `rmtree` только внутри корня профилей).
* **Свои папки выгрузки.** `create_profile()` всегда пишет `DISK_DIR` и
  `UNLIM_DIR` в `.env` нового профиля. Если пути не заданы, берётся
  `<корень выгрузки>\Клиенты\<имя профиля>\Disk|Unlim` — иначе файлы клиента
  легли бы в папки Сергея (у основного профиля это `D:\YandexDiskBackup\Disk`).
* **Переключение.** `POST /api/profiles/switch` проверяет, что не идут задачи
  (`tm._tasks`, `pipeline`, `full_cycle`), пишет `switch_profile.ps1` в
  `LOG_DIR` и запускает его через `powershell.exe` с
  `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`; помощник ждёт выхода
  программы (`Wait-Process -Id <pid>`), ставит `$env:YADISK_DATA_DIR` на папку
  профиля и запускает exe. Через 1.2 с вызывается `_quit_application()`.
  Из исходников переключение недоступно: запускать нечего — возвращаем
  подсказку про `YADISK_DATA_DIR`. Воркеры (`TaskManager`) и так наследуют
  `YADISK_DATA_DIR` из окружения, поэтому задачи пишут в профиль.
* **Роуты.** `GET /api/profiles`, `POST /api/profiles/create|rename|delete|switch`.
  `/api/status` отдаёт `profile` текущего профиля — по нему обновляется пилюля
  «👤 имя» в шапке (`pill-profile` в `PILL_TARGETS` ведёт на `#profiles-card`).
* **UI.** Карточка «Пользователь» в «Настройках»: список профилей с путями,
  кнопки «Переключиться», «Переименовать», «Удалить»; «Создать профиль» —
  окно с именем и папками выгрузки. Шаблон строки рендерится в
  `renderProfiles()`; в `onclick` передаётся индекс, а не имя, — имена с
  кавычками не ломают разметку.

### Окно «Что нового в версии X»

* `updater.check_for_updates()` и раньше отдавал `notes` — тело релиза GitHub
  (первые 2000 символов). Теперь оно показывается в отдельном окне
  `#update-modal`, а не мелким блоком в карточке.
* `showUpdateModal()` заполняет заголовок, подзаголовок и справку
  (`_notesText()` снимает markdown: заголовки `#`, `**жирный**`, `` `код` ``

## 34. Октябрь 2026: выбор «что качать», одна копия программы, снимки баз (v35.7.2)

Три вещи одной версией: качать не всю очередь, а отмеченное; не открывать
второе окно поверх работающего; иметь точку, к которой можно вернуть базы.

### Проводник облака (`selection.py`, `#picker-card`)

* **Выбор — список работ, а не пометка в базе.** Это главное решение.
  Первая мысль была «пометить в базе только выбранное» — но тогда любой
  ошибочный выбор менял бы очередь, и вернуть её можно было бы только сбросом
  статусов. Вместо этого `selection.build_disk_jobs()` собирает готовые
  `DownloadJob` и отдаёт их `downloader.download_all(jobs=...)` — механизм,
  который уже умел качать точный список. Статусы pending/failed/lost у
  невыбранных файлов не трогаются вообще; скачанные остаются скачанными.
* **`selection.py`.** `selection.json` в `DATA_DIR` профиля:
  `{"version": 1, "disk": {"folders": [...], "files": [{"path", "size"}]}}`.
  Запись атомарная (`.tmp` + `os.replace`), битый JSON читается как пустой
  выбор. `MAX_ENTRIES = 50000`. Пути нормализуются: `Фото/2024`, `/Фото/2024`
  и `disk:/Фото/2024` — одно и то же; `..` запрещены.
* **Сборка работ.** Для папок сначала идёт `downloader.scan_tree()` — так в
  базу попадают новые файлы (без этого выбранная папка, добавленная в облако
  после последнего скана, не дала бы ничего). Затем
  `state.get_files_under(folders)` берёт только `pending/failed/lost` —
  скачанное и пропущенное не перекачивается. Явно выбранные файлы
  проверяются `state.get_statuses()`: `downloaded`/`skipped` считаются в
  `already_done` и отбрасываются. Падение `scan_tree` на одной папке
  записывается в журнал и не срывает запуск.
* **`main.py download --selection`.** `_download_selection()` собирает работы
  и вызывает `download_all(..., jobs=jobs, ...)`; `--no-scan` от веб-окна
  (проводник уже отсканировал выбранные папки).
* **Роуты.** `GET /api/cloud/list?path=...` — содержимое папки облака с
  размерами, датой и `status` из базы; `GET/POST /api/selection/disk`,
  `POST /api/selection/disk/clear`; `POST /api/disk/download_selection` —
  отказ на пустом выборе и недоступной папке выгрузки, запуск задачи.
* **UI.** Карточка «Что качать» в «Настройках»: «Открыть облако», «↑ Вверх»,
  путь, список с галочками, сводка «папок N, файлов M, ≈ объём», «Скачать
  выбранное», «Снять всё». Скачанные файлы рисуются с неактивной галочкой и
  подписью «уже скачан»; файл внутри отмеченной папки — «в выбранной папке».
  Отметка папки не разворачивает тысячи файлов: серверная выборка по
  префиксу пути.

### Одна копия программы (`single_instance.py`)

`launcher.choose_port()` подбирает свободный порт, поэтому второй запуск
раньше молча открывал второе окно на другом порту — две копии писали в одни
базы и лог. Теперь `launcher.py` сразу после настройки журнала берёт
Windows-мьютекс `Local\YadBackup-single` (`CreateMutexW` +
`ERROR_ALREADY_EXISTS`); на других системах — flock на
`BASE_DATA_DIR/app.lock`. Не взялось — окно сообщения «Yad.backup уже
запущен… значок в трее» и выход с кодом 0. Блокировка не зависит от профиля:
одна работающая программа на пользователя, профиль меняется только
перезапуском. Мьютекс освобождается при завершении процесса сам.

### Снимки баз — точка отсчёта (`dbsnapshots.py`, `#snapshots-card`)

* Снимок делается SQLite backup API: копировать файл живой WAL-базы нельзя.
  `make_snapshot()` снимает обе базы (`state.db` и `unlim_state.db`),
  имена — `<вид>-ГГГГММДД-ЧЧММСС.db` в `DATA_DIR/snapshots`; при совпадении
  секунды добавляется `-N`.
* `KEEP = 5` снимков на каждый вид; сортировка и обрезка — по `(mtime, name)`,
  потому что два снимка в одну секунду по имени сравнивались бы неверно.
* `restore(name)` проверяет имя (`_resolve()`: только голое имя файла, вид из
  белого списка) и копирует снимок обратно в базу тем же backup API.
* `POST /api/db/restore` сначала требует остановить выгрузку (`_db_running`),
  затем сам делает снимок `before-restore` — откат тоже обратим.
* UI — карточка «Снимки баз» в «Диагностике»: «Сделать снимок», «Обновить
  список», по снимку — «Восстановить» (с подтверждением) и «Удалить».

### Переключение профиля

Помощник `switch_profile.ps1` теперь сначала просит окно закрыться штатно
(`WaitForExit(10000)`), и только если процесс остался — `Stop-Process -Force`.
Раньше профиль переключался поверх живого процесса, который продолжал писать
в старую папку данных.

Тесты: `tests/test_selection.py` (11 проверок: нормализация и запрет `..`,

## 35. Октябрь 2026: календарь дат Безлимита (v35.7.3)

У Безлимита нет папок — есть плоская лента файлов, нарезанная кластерами.
Раньше «что качать» работало только для Диска (папки и файлы). Теперь такой
же выбор есть у Безлимита: отметьте дни в календаре — скачаются только файлы
этих дней.

### Как устроен кластер и почему фильтр — сравнение диапазона

`cluster_id` Безлимита — строка `"<начало>_<конец>"`, оба числа — unix-время
в миллисекундах, дополненное нулями до 19 знаков. Поэтому строковый порядок
`cluster_id` совпадает с хронологическим, и фильтр по дню — это обычное
`cluster_id >= '…' AND cluster_id < '…'`, а не `substr`/`datetime()` по каждой
строке: индекс `idx_unlim_cluster` (миграция 6 в `unlim_schema.py`) делает
такую выборку быстрой даже на сотнях тысяч файлов.

Днём кластера считается день его **начала** (локальное время). Кластер может
пересекать полночь — съёмка с 23:50 до 00:20 считается днём 2-го числа и не
попадает в 3-е; иначе один кластер удваивал бы счётчики двух дней.

### `unlim_dates.py`

* `parse_cluster_id()`, `cluster_start_ms()`, `ms_to_date()`, `date_to_ms()` —
  разбор и перевод времени, без обращений к базе.
* `merge_dates()`, `clean_ranges()`, `expand_ranges()` — дни хранятся
  **диапазонами** (`[["2024-05-01","2024-05-02"], ["2024-05-05","2024-05-05"]]`):
  один диапазон — одно сравнение в SQL. Битые даты и наложение отбрасываются,
  `MAX_DAYS = 20000` ограничивает бессмысленный выбор.
* `range_clause()` — SQL-условие и параметры; пустой выбор даёт `1 = 0`,
  чтобы случайный «пустой фильтр» никогда не означал «всё».
* `calendar()` — чтение базы **только на чтение** (`utils.sqlite_ro_uri`),
  чтобы календарь не мешал идущей выгрузке: по месяцам считает файлы, байты,
  скачанные, остаток и число кластеров на день.
* `selection_stats()` — сводка по выбранным дням для окна и для проверки
  «нечего качать».

### Выбор хранится в профиле, статусы не меняются

`selection.json` получил второй раздел:

```json
{"version": 1,
 "disk": {"folders": [], "files": []},
 "unlim": {"ranges": [["2024-05-01", "2024-05-02"]]}}
```

`selection.save_unlim_dates()` хранит диапазоны, `clear_unlim()` снимает
только дни, `save_disk()`/`clear_disk()` дни не трогают — выбор Диска и
Безлимита независимы. Главное правило то же, что в 35.7.2: это **фильтр при
запуске**, а не пометка в базе. Невыбранные файлы остаются в очереди как
стояли; скачанные остаются скачанными; повторно скачанные дни в календаре
отметить нельзя (клетка показывает «✓ всё» и неактивна).

### Три загрузчика

Фильтр `cluster_ranges` добавлен во все пути скачивания, иначе выбор
действовал бы только для одного режима:

* `unlim_backup.take_batch(..., cluster_ranges=None)` и
  `reset_skipped_files(db_path, media_type="all", cluster_ranges=None)` —
  сбойные (`skipped`) сбрасываются в очередь только внутри выбранных дней;
* `unlim_worker.take_batch(worker_id, size, cluster_ranges=None)`;
* `unlim_direct.take_batch(..., cluster_ranges=None)`.

Все три получили ключ `--selection` (читает `selection.unlim_ranges()`);
пустой выбор — выход с сообщением «В календаре Безлимита не отмечено ни
одного дня — скачивать нечего».

### Роуты и окно

* `GET /api/unlim/calendar?month=ГГГГ-ММ` — дни месяца и текущий выбор;
* `GET/POST /api/selection/unlim`, `POST /api/selection/unlim/clear`;
* `POST /api/unlim/download_selection` — отказ на пустом выборе
  («Сначала отметьте дни в календаре») и когда `left <= 0`
  («В выбранных днях всё уже скачано»); иначе задача
  `unlim_backup.py --selection --target all --media all --out-dir … --workers …`
  (и `--no-previews`, если превью отключены).

Карточка «Даты Безлимита» (`#unlim-dates-card`) в «Настройках»: навигация по
месяцам и «Сегодня», сетка Пн–Вс, клетка дня с числом и подписью
«N осталось» / «✓ всё», сводка «Отмечено дней: N · файлов M · уже скачано K ·
осталось L», кнопки «Скачать выбранные даты» и «Снять всё». Отметка
сохраняется с задержкой 250 мс (не запрос на каждый клик). Пустые дни и дни,
где всё скачано, не отмечаются.

### Авто-возврат сгоревших файлов

Файл, получивший `SERVER_FAIL_LIMIT` ответов 5xx, уходит в `lost` и получает
`retry_after = now + LOST_RETRY_SEC` (30 минут). В начале каждого запуска
`State.return_lost(limit=LOST_RETURN_LIMIT)` (200) и
`unlim_backup.return_lost_files(db_path, limit, cluster_ranges)` возвращают в
`pending` только просроченные файлы, самые старые первыми.

* `server_fails` **не** обнуляется: сгоревший файл при первом же новом 500
  снова `lost`, а не тратит ещё три попытки. Кнопка «Попробовать»
  (`reset_lost`) по-прежнему обнуляет счётчик.
* Один раз за запуск: в `FullCycle` проходы `p > 1` вызывают воркеры с
  `--no-return-lost`, поэтому внутри полного цикла файл не возвращается
  повторно.
* В режиме дат («Скачать выбранные даты») возвращаются только файлы внутри
  выбранных дней — `cluster_ranges` превращается в SQL-условие
  `unlim_dates.range_clause`.
* Выбор «Что качать» авто-возврат не делает: jobs уже включают `lost`.
* Журнал пишет «Сгоревших возвращено в очередь: N» только когда N > 0.

## 37. Ноябрь 2026: «Файлы переехали?», честная сортировка, «Ждут Яндекса» (v35.7.5)

Первый внешний пользователь (vovapuh) перенёс файлы и отсортировал папку

пусть клиент укажет папку, а программа сама сверит базу с диском; пусть
сортировку можно отменить кнопкой; пусть отчёт сортировки действительно
показывает, куда что ляжет.

### `relocate.py` — поиск и перепривязка

Новый модуль `relocate.py` (не CLI, а библиотека для `webui.py`):

* `load_rows(scope)` — скачанные файлы с непустым `local_path`; чтение через
  `mode=ro`;
* `detect_old_root()` — старый корень выгрузки по настройке, по общему
  префиксу путей и по каждой букве диска отдельно; `_score_root()` выбирает
  тот, от которого по точному пути находится больше файлов;
* `plan_relocate(scope, new_root, old_root_hint)` — классификация: `already`,
  `by_path` (точный хвост), `by_name` (имя и размер в подпапках — лечит
  сортировку и суффикс `_1`), `by_md5` (когда имя+размер совпали у нескольких
  файлов), `conflicts`, `missing`, `offline` (`utils.volume_ready()`:
  буква диска не подключена — файл не потерян);
* `apply_relocate(plan)` — `UPDATE ... SET local_path` в транзакции;
* `requeue_missing(scope, keys)` — только перечисленные файлы: `pending`,
  `local_path = NULL`, сброс попыток и пауз;
* `plan_restore_cloud()` / `apply_restore_cloud()` — обратная операция
  сортировки для Диска: цель считается `utils.resolve_local_path(root,
  remote_path)`, занятая цель не перезаписывается (конфликт), пустые папки
  после переноса удаляются.

`Plan.as_dict()` отдаёт `missing_keys`/`offline_keys`, чтобы окно могло
вернуть в очередь ровно те файлы, что не нашлись.

## 38. Ноябрь 2026: сверка с облаком (v35.7.6)

### Зачем

`scan`/«Пересоздать базу» стирают статусы, `verify` смотрит только диск и в
облако не ходит. Нужен безопасный осмотр: что сейчас реально лежит в Яндексе
и как это сходится с базой — особенно когда файлы добавляли или удаляли с
телефона, другого компьютера или через сайт Яндекса.

### `cloud_audit.py`

* `scan_disk_cloud(token)` — BFS по всему дереву через `downloader._list_dir`
  (корзина пропускается), возвращает `{путь: {name,size,md5}}`; в базу ничего
  не пишет.
* `scan_unlim_cloud(cookies_path)` — повторяет запросы сбора базы Безлимита
  (`photo-init-snapshot` → `photo-get-snapshot` → батчи по 50 через
  `photo-get-clusters-with-resources`), не трогая `unlim_files` и
  `unlim_clusters`; кластер, который сервер не вернул, повторяется до трёх раз.
* `load_db_rows(scope)` — read-only чтение всех строк обеих баз (не только
  скачанных: файл в очереди тоже сверяется).
* `compare()` — `same` (размер и MD5 совпали), `new` (в облаке есть, в базе
  нет), `changed` (размер или MD5 другой), `gone` (в базе есть, из облака
  исчез). Строка со статусом `deleted`, снова появившаяся в облаке, считается
  `new`.
* `run(scope)` — обходит одну или обе базы, пишет прогресс в
  `logs/cloud_audit_status.json`, полный план — в `logs/cloud_audit_plan.json`,
  полный список — в `logs/cloud_audit.csv` (`;`, utf-8-sig), читаемый отчёт —
  в `logs/cloud_audit_report.txt` (время, базы, цифры, первые 100 файлов по
  каждому списку, что нажали и сколько изменилось).
* `add_new()` — новые и изменившиеся файлы встают в очередь. У изменившегося
  старая локальная копия переименовывается (`old_copy_path()`:
  `Отчёт_старая.docx`, при занятом имени `_старая_2`), после чего
  `local_path=NULL`, `status='pending'`. Диск не подключён или файл занят —
  файл не трогается, причина попадает в результат.
* `mark_gone()` — `status='deleted'`, `error='удалён из облака'`; `local_path`
  и файл на диске остаются. Повторное нажатие ничего не меняет.
* Действия пишутся в `logs/cloud_audit_actions.json`; отчёт пересобирается,
  поэтому «что нажали» всегда видно в `cloud_audit_report.txt`. Перед новой
  сверкой список действий очищается.
* `write_error()` / `write_stopped()` — чтобы окно не висело в «идёт» после
  сбоя или кнопки «Остановить».

## 40. Ноябрь 2026: сверка без ложных «изменилось», статусы баз в отчёте (v35.7.8)

### Причина

Сверка 35.7.6 на реальном облаке показала 47 116 «изменившихся» файлов
Безлимита — ровно все скачанные. Оказалось, API
`intapi/photo-get-clusters-with-resources` теперь возвращает для файла только
`id`, `itemId`, `width`, `height`, `albums`: ни `size`, ни `name`, ни `md5`.
`scan_unlim_cloud()` превращал отсутствие размера в `0`, в базе же размер
настоящий (записан при скачивании), поэтому `_differs()` видел «17 МБ → 0 Б»
у каждого файла. «Совпадали» только те 546 записей, у которых и в базе `0`
(538 `lost` + 8 `pending`).

### Что сделано

- `scan_unlim_cloud()`: отсутствующий или нулевой `size` сохраняется как
  `None` («неизвестно»). `_differs()` при `None` размер не сравнивает —
  сравнение идёт по наличию (`file_id`) и MD5, если он есть.
- `_same_detail()`: для «совпадает» поясняет, что «размер в облаке не
  отдаётся — сверено по наличию», а также помечает `lost` («сгорел у
  Яндекса») и `pending`/`in_progress` с `error LIKE 'storage_down%'`
  («ждёт Яндекса»). Пояснения попадают в CSV и в отчёт.
- `load_db_rows()` читает `error`; `_base_stats()` считает по каждой базе
  `downloaded`, `lost`, `waiting`, `pending`, `statuses` и
  `cloud_size_unknown`. Всё это лежит в `per_base` статуса сверки.
- Отчёт: под строкой базы — «скачано · сгорело · ждут Яндекса · в очереди»,
  отдельная строка «размер в облаке не отдаётся: N файлов — сверены по
  наличию» и строка в ИТОГЕ, почему `changed` может быть 0. Старые статусы
  без новых полей рендерятся без нулей.
- UI (`renderCloudAudit`): блок `#audit-bases` показывает разбивку по базам
  после завершения сверки; объясняет расхождение с «Главной», где «сгорело»
  и «ждут Яндекса» считаются по двум базам вместе (587 = 538 + 49,
  244 = 8 + 236 на данных Сергея 01.11.2026).

### Тесты

`tests/test_cloud_audit.py`: неизвестный размер не делает файл изменившимся;
пояснения для `lost`/`waiting`; `scan_unlim_cloud` сохраняет `None`; полный
проход пишет в `per_base` статусы и «размер не отдаётся» в отчёт. В
`tests/test_packaging.py` проверяется `#audit-bases` и `cloud_size_unknown`.
Всего 625 тестов; `ruff --select F,E9` и `node --check` чисто.

## 41. Ноябрь 2026: превью с авторизацией, объединённые настройки (v35.7.9)

### Почему превью не качались

Проверка 02.11 показала: папка `previews` пуста, в обеих базах 0 записей
`preview_path`, хотя настройка `previews: true`. Причина — Яндекс отдаёт
ссылку на превью только авторизованному клиенту: анонимный запрос получает
`403 text/html`, а с куками или заголовком `Authorization: OAuth <токен>` —
`200 image/jpeg` (проверено вживую для обеих баз). Программа качала превью
анонимно: у Безлимита `save_from_link(link, dst, dead_hosts=DEAD_HOSTS)` без
`session=`, у Диска `_get_thread_http_session()` без кук и токена. `403`
глотался в `except`, поэтому в журнале была тишина.

### Что сделано

- `fetch.fetch_to_file()` принимает `headers` и добавляет их только к первому
  запросу — самой ссылке от API. Подписанный редирект на сервер хранения
  токен не получает.
- `previews.make_disk_preview()` берёт токен из клиента (`client.token` или
  явный параметр) и шлёт `Authorization: OAuth …`.
- `unlim_backup.save_preview_for_deferred()` качает превью в той же сессии с
  куками (`session=session`).
- `previews.preview_path_for(kind, source)`: две плоские папки
  `<корень>/disk` и `<корень>/unlim`, без структуры облака. Имя —
  `<имя>__<sha1(source)[:8]>.jpg`: одинаковые `IMG_0001.JPG` из разных папок
  не затирают друг друга, путь стабилен.
- `state.mark_downloaded()` и `mark_skipped()` возвращают путь прежнего
  превью; `downloader._apply_result()` сразу удаляет файл. У Безлимита
  `unlim_backup.mark_done()` делает то же: читает `preview_path`, обнуляет
  колонку и удаляет файл.
- `migrate_legacy_previews()` раскладывает старые `_превью` по `disk`/`unlim`.
  Смена папки превью по-прежнему переносит дерево целиком и правит пути в
  обеих базах — подпапки сохраняются.
- Превью не меняет статус файла и не попадает ни в один счётчик «скачано»:
  у Диска результат остаётся `deferred`, у Безлимита — `pending`/`lost`.

### UI

- `#export-dirs-card` «Папки выгрузки» — вкладки «Обычный Диск» и «Безлимит»
  (`data-ctab` / `data-ctab-panel`, классы `.ctab`, не пересекаются с верхними
  `.tab`). Вместо отдельных `#unlim-dir-card` и `#disk-dir-card`.
- `#access-card` «Доступ к Яндексу» — вкладки «Токен» и «Куки браузера».
  Вместо `#token-card` и `#cookies-card`.
- `switchCardTab(cardId, name)` переключает вкладку; `gotoSetting(panel,
  selector, cardId, tab)` сначала открывает вкладку, потом прокручивает к
  полю. `PILL_TARGETS` для `pill-token`, `pill-cookies`, `pill-session`,
  `pill-disk-session` содержит `card` и `tab`, поэтому плашки попадают в
  видимое поле.
- Ручки раздвижения перенесены на новые id; список в `makeResizable` обновлён.

## 43. Ноябрь 2026: токен через браузер, «Написать разработчику» (v35.8.1)

### Полуавтоматическое получение токена

`fetch_token.py` повторяет подход `fetch_cookies.py`: запускает видимое окно
Chrome (или встроенного Chromium), открывает `https://yandex.ru/dev/disk/poligon/`
и ждёт входа в аккаунт по кукам `Session_id`/`yandexuid`/`sessionid2`. После
входа скрипт один раз перезагружает страницу, нажимает «Получить OAuth-токен»
и ищет токен `y0_…` в полях ввода, тексте страницы, адресе и
`localStorage`/`sessionStorage`. Найденный токен проверяется запросом к
`https://cloud-api.yandex.net/v1/disk/` и сохраняется в `.env` как
`YA_DISK_TOKEN` через `dotenv.set_key(..., quote_mode="never")`. Сам токен в
файл статуса не пишется — только логин.

Статус — `logs/token_fetch_status.json` (`paths.TOKEN_FETCH_STATUS`), состояния
`running`/`done`/`cancelled`/`stopped`/`timeout`/`error`. `webui.py`:

- `token_fetch_status()` читает статус; если файл говорит `running`, а задачи
  `token_fetch` в `TaskManager` уже нет, показывает `stopped`; при `done`
  один раз перечитывает `.env` (`load_dotenv(..., override=True)`), чтобы UI
  увидел новый токен без перезапуска;
- `POST /api/token/fetch` запускает `fetch_token.py`, `POST
  /api/token/fetch/cancel` останавливает и пишет `cancelled`;
- `worker_scripts`/`yadisk_backup.spec` включают `fetch_token`, иначе в
  frozen-сборке запустился бы GUI вместо воркера.

В интерфейсе вкладки «Токен» сверху появился блок `#token-fetch-area` с
кнопкой «Получить токен», отменой и статусом (`renderTokenFetch`), ручной ввод
убран под `details#token-details` «Дополнительно: вставить токен вручную».
Плашка `pill-token` теперь ведёт к `#btn-token-fetch`.

### «Написать разработчику»

Форма живёт в карточке `#diag-report-card` рядом с диагностическим отчётом:
имя, почта, телефон (необязательно), текст до 4000 символов, галочка согласия

вашими данными у разработчика нет: сообщение придёт в Telegram и останется в

- `POST /api/diagnostics/feedback` (`FeedbackPayload`) проверяет имя, почту,
  длину полей, текст и согласие; при `attach_report` собирает отчёт через

### 403 — не «удалён навсегда»

- `Beast._mark_unavailable()` делит причины:
  - диск: `failed` + (`PathNotFound`/404/410) после 3 попыток → `deleted`;
  - диск: `failed` + 403 после 3 попыток → **`denied`**;
  - Безлимит: `skipped`/`failed` + (404/410/«Ссылка не найдена») → `deleted`;

- `denied` не входит в `_remaining()`, поэтому «Зверь» не крутит такие файлы
  вечно и завершается. Скан (`ON CONFLICT`) статус не меняет, автоматического
  возврата нет.
- Ручной возврат: `POST /api/reset {what:'lost'}` теперь обновляет
  `status IN ('lost','denied')` → `pending`, обнуляя `server_fails`,
  `retry_after` и `attempts`. UI считает `#reset-lost` как `lost + denied`
  обеих баз, `lostTotal()` тоже; «Попробовать» подхватывает оба статуса.
- `db_stats()` отдаёт `denied` (в `total`/`bytes_total`, как `failed`),
  `queueLeft()` и итог запуска включают его в «отложено».

## 48. Ноябрь 2026: журнал скачивания — имя, вес, прогресс, сервер (v35.8.6)

### Зачем

Сергей запустил выгрузку и увидел, что журнал молчит, пока качается файл на
20 ГБ: непонятно ни что именно качается, ни сколько осталось, ни с какого
сервера. Заодно выяснилось, что полосы `tqdm` попадают в stdout дочернего
процесса (Web UI запускает задачу с `stderr=STDOUT`) и склеиваются со строками
журнала в одну длинную простыню.

### Новый модуль `progress.py`

- `FileProgress(name, size)` — строки одного файла; `emit` подменяется в
  тестах, `clock` — управляемые часы.
- `start()` — для крупных файлов (от `BIG_BYTES = 100 МБ`) пишет
  `⬇ имя · вес · начинаю`.
- `update(written, host, total)` — вызывается на каждом чанке; строка
  обновляется не чаще `STEP_SEC = 10` секунд:
  `⬇ имя · 12% · 250 МБ из 2,1 ГБ · 4,1 МБ/с · host · осталось ~8 мин`.
  Если счётчик пошёл назад (повтор по новой ссылке после 5xx), отсчёт
  начинается заново; скорость не показывается, пока прошло меньше 0,5 с.
- `done(written, host, seconds)` — итог для любого файла:
  `✅ имя · 2,1 ГБ · 27 мин · host`.
- `stopped(reason)` — крупный файл оборвался:
  `⏸ имя · остановился на 12% · 250 МБ из 2,1 ГБ · host · причина`.
- `human_size()` — русские единицы с запятой (`20,9 ГБ`, `512 КБ`);
  `human_span()` — `0,4 с` / `18 с` / `27 мин` / `2 ч 10 мин`.
- Строка пишется и в `logging` (файл журнала), и в `print` (stdout задачи,
  который читает Web UI).

### Точки вызова

- `fetch.py`: `fetch_to_file(progress=…)` вызывает `progress(written, host)`
  после каждого чанка рядом с `heartbeat()`.
- `downloader.py`: `_download_one()` создаёт `FileProgress(job.remote_path,
  job.size)` после проверок «уже скачан»/«мало места», передаёт
  `file_progress.update` в `_transfer()` → `fetch_to_file`, вызывает
  `stopped()` на `FetchFailure` и `done()` на успехе.
- `unlim_backup.download_one_file()`: те же строки для прямой выгрузки
  Безлимита (`mpfs/url`), сервер — `hostname` ссылки.
- `unlim_worker.download_and_extract()`: строки для ZIP-пачки, вес из
  `Content-Length` (если сервер его отдал).

### Полосы tqdm

- `downloader.download_all()`: `file_bar`/`byte_bar` получили `disable=None`
  — рисуются только в настоящем терминале.
- `main.py` (сканирование, проверка MD5) и `unlim_download.py` — так же.
- `unlim_backup.py`: строка `Батч #N: …` с `\r` печатается только при

- `report_status.py` читает скорость и остаток из новых строк

## 50. Ноябрь 2026: докачка по Range, сторож тишины, пробы мёртвых серверов (v35.8.8)

`unlim_backup.download_one_file` обрывал скачивание по жёсткому лимиту
`deadline = max(120, timeout × 60)` (с v35.4.4) — при тактике с `timeout=7`

рвал соединение; `DeadHosts` помечал его мёртвым на 30 минут и дальше
пропускал без запроса — даже если Яндекс уже вернул сервер в строй.

### Докачка `.part` по Range

- `fetch.part_path_for(dst)` теперь детерминированный:
  `.yadisk-<sha1(dst)[:16]>.part` рядом с целевым файлом. Один и тот же путь
  всегда даёт один и тот же обрывок, поэтому следующая попытка его находит.
  Имя не `<имя>.part`, чтобы не затереть настоящий файл с таким именем и не
  упереться в лимит длины пути.
- `fetch_to_file` перед первым запросом считает размер `.part` и, если он
  есть, добавляет `Range: bytes=N-`. Ответ `206` — файл дописывается в режиме
  `"ab"`, `written` начинается с `N`; ответ `200` (сервер не умеет Range) —
  `.part` усекается и качается заново; `416` — обрывок удаляется, ошибка
  `bad_file`. MD5 при докачке считается по всему файлу: сначала в хеш
  подмешивается уже скачанное.
- Сетевые ошибки `requests` (`Timeout`, `RequestException`) больше не удаляют
  `.part`: они ловятся раньше `OSError` (наследником которого являются) и
  оставляют байты для докачки. Обрывок удаляется только при локальной ошибке
  (`OSError`: место, права), при несовпадении размера/суммы и при
  недеферрабельных HTTP-кодах (403/404) — файла уже нет, хранить нечего.
- `downloader._download_one` сообщает `FileProgress.resumed(размер .part)`,
  `unlim_backup.download_one_file` делает то же по своему `.part`.
  `progress.FileProgress` получил поле `_base`: проценты и «осталось»
  считаются от всего файла, скорость — только по новым байтам, а строка
  старта выглядит как `↻ имя · продолжаю с 45% · 2,3 ГБ из 5,0 ГБ`.
  Прошлые версии Безлимита оставляли `<имя>.part` — `_part_path_for_file`
  один раз переименовывает его в новое имя.

### Сторож тишины вместо жёсткого лимита

`deadline` из `unlim_backup.download_one_file` удалён. Скачивание рвётся
только когда сервер молчит дольше `timeout` секунд (read-таймаут `requests`);
в журнал и в ошибку файла пишется `нет данных N с` вместо имени исключения.
В `fetch_to_file` таймаут тоже переведён на понятный текст — `нет данных 10 с`
для сервера хранения и `нет данных 60 с` для ссылки от API.

### Пробы мёртвого сервера у «Зверя»

- `DeadHosts(probes=…)` и переменная окружения `YADISK_DEAD_HOST_PROBES`
  задают, сколько настоящих запросов разрешить помеченному мёртвым хосту до
  истечения TTL. `mark()` сбрасывает счётчик проб, `is_dead()` остался чистой
  проверкой для журнала, новая `allow()` списывает пробу и возвращает
  «можно/нельзя».
- `fetch_to_file` проверяет хост через `allow()`; `unlim_backup` — на входе в
  `download_one_file` (раньше `is_dead`).
- `TaskManager.start(..., env_extra=…)` добавляет переменные к окружению
  дочернего процесса; `Beast._start_lane` передаёт
  `{"YADISK_DEAD_HOST_PROBES": "3"}`, поэтому оба дочерних процесса (Диск и
  Безлимит) получают по три пробы на круг. Обычные ручные запуски по-прежнему
  пропускают мёртвый хост без запроса.

### Признак задачи: выгрузка, скан или служебное

- `webui.task_kind(script, args)` классифицирует запуск: `main.py download` и
  `main.py retry-failed` — `download`; `unlim_backup.py` без `--scan-only` —
  `download`; `main.py scan/verify`, `unlim_backup.py --scan-only`,
  `unlim_download.py --collect` — `scan`/`other`.
- `Task` хранит `kind`, `TaskManager.status()` отдаёт его в словаре задачи.
- `build_session` строит сессию только из задач с `kind == "download"`
  (записи без `kind` считаются выгрузкой — совместимость с тестами и старыми
  вызовами). Поэтому скан в слотах `disk`/`unlim` не создаёт нулевую сессию и
  `remember_sessions` не перезаписывает `logs/last_session.json`; плашка
  берётся из сохранённого итога.

### «Зверь» копит итог по линиям

- `Beast.gained_by_kind = {"disk": 0, "unlim": 0}` сбрасывается в `start()`;
  `_run_round` прибавляет к нему `max(0, after[k][0] - before[k][0])` по
  каждой линии (счётчик `downloaded` в базе). `status()` отдаёт
  `gained_by_kind`.
- `build_session(..., beast_st=...)`: «Зверь» владеет сессией, если стартовал
  позже полного цикла. `success` = накопленный итог линии плюс живые цифры
  текущего круга, если задача линии идёт и её статус свежий. После остановки
  итог остаётся; ручная выгрузка со `started_at > finished_at` «Зверя»
  начинает новую сессию. В сессии есть `beast: true`, `round`, `strategy`;
  UI пишет в подсказке «Круг N · тактика «…»» вместо «Проход N из M».
- Задачи-линии «Зверя» стартуют внутри сессии и владельца не меняют — для
  этого сравнение идёт с `finished_at`, а не просто с последним `started_at`.

### Журнал «Зверя» и прогресс

- UI в режиме «Зверя» выводит `b.log`, затем хвосты `log_tail` задач `disk` и
  `unlim` (по 160 строк) с заголовками `── Диск ──` / `── Безлимит ──`. Так
  видны строки `⬇ имя · вес · скорость` дочерних процессов.

  `⬇ имя · 1,0 МБ · начинаю · вес неизвестен`; промежуточные строки — с
  `UNKNOWN_BYTES = 10 МБ` (`BIG_BYTES = 100 МБ` для известного веса остаётся).

- `diagnostics.changelog_section(limit=2)` включает в ZIP-отчёт раздел текущей

### Исключения из выгрузки (`exclusions.py`)

- Список облачных путей хранится в `paths.DATA_DIR/exclusions.json` как
  `{"items": [...]}`; запись атомарная (временный файл + `os.replace`).
  `normalize_items` приводит слэши к прямым, убирает хвостовой `/`, пустые и
  корень `disk:/`, отбрасывает относительные пути и дубликаты.
- `is_excluded(remote_path, items)` — точное совпадение или вложенность
  (`disk:/Photos` покрывает `disk:/Photos/2024/a.jpg`, но не
  `disk:/Photoshop/...`). Файл в корне (`disk:/a.jpg`) исключается точно.
- `sync_db(items)` переводит строки таблицы `files` в статус `excluded` и
  возвращает `pending` при снятии; статусы `downloaded`/`skipped`/`deleted`
  сохраняются, `error` очищается. Без базы — `{"excluded": 0, "returned": 0}`.
- Сканер Диска (`downloader.py`) загружает список один раз и помечает
  исключённые `state.mark_excluded`; `cloud_audit` пропускает исключённые
  папки/файлы и не считает их пропавшими; `db_stats` отдаёт `excluded`
  отдельной цифрой.
- API: `GET/POST /api/config/exclusions`. POST отказывает, пока идут задачи
  (`disk`, `unlim`, `verify`, `organize`, `audit`), делает авто-копию базы
  `before-exclusions`, затем `sync_db` и `save`. UI — кнопка
  «🚫 Не выгружать из диска…» на «Главной» и ссылка в пошаговом режиме; окно с
  деревом облака, галочками на папках и файлах. Только Обычный Диск.

### Сторож против «Зверя»

- `DiskWatchdog._stop_everything` первым вызывает `beast.stop()`, затем
  останавливает полный цикл и слоты. `Beast._start_lane` и `_run_round`
  проверяют `self._stop` — после срабатывания сторожа новый круг не начнётся,
  автоперезапуска нет.
- `_fatal_reason` дополнительно распознаёт `disk_full` у обеих линий и
  `disk_offline` у Диска и прекращает круги с понятным сообщением.
- `POST /api/disk/resume`: «Продолжить» в оранжевой плашке. Проверяет папку

### Журнал: выделение и прокрутка

- `renderConsole(id, lines, placeholder)` сначала ищет самый длинный хвост
  старого журнала, совпадающий с началом нового (сервер может обрезать старые
  строки), затем — общий префикс. Если префикс есть, пересобираются только
  строки после него: `while(el.children.length > same) el.lastElementChild.remove()`.
  Выделенный мышью текст в неизменных строках остаётся выделенным.
- Если не совпало ничего (другая задача), окно пересобирается через
  `replaceChildren`.
- `_capConsole(id, el, stick)` держит не больше `MAX_CONSOLE_LINES = 4000`
  строк, снимая их сверху и компенсируя `scrollTop`, когда человек читает

  пишет `grip.textContent = '⠿'`, значок рисует `.card-drag::before`.

### «Файлы переехали?» и путь у воркера

- `relocate.load_rows` берёт оба статуса (`downloaded`, `skipped`) и строки
  с пустым `local_path`: имя для поиска — `basename(remote_path)` у Диска и
  `name` у Безлимита.
- Фильтр «Старая папка» (`only_under`) не отбрасывает строки без пути:
  `if not r.local or relative_under(...) is not None`.
- Строка без имени сразу считается `missing` (не `offline`), а не гоняется
  через `_Index.find`.
- Пустой путь не делает файл «на отключённом диске»: `volume_ready("")`
  возвращает False, поэтому проверка заменена на `elif not local or volume_ready(local)`.
- `unlim_worker.mark_done` принимает `(file_id, local_path)` и пишет путь в
  базу (`COALESCE(?, local_path)` — вызов без пути старый путь не затирает).
  `match_extracted` возвращает `[(file_id, путь_внутри _unlim)]`, а
  `split_by_extracted` осталась обёрткой для прежних вызовов и тестов.
- `download_and_extract` отдаёт относительный путь внутри `_unlim`, а не только
  имя файла.

### Безопасные имена на Windows

- `unlim_direct` и `unlim_backup` кладут файл под `utils.sanitize_component(name)`;
  в базе остаётся яндексовое имя. Колонки `< > : " / \ | ? *` и хвостовые
  пробелы/точки заменяются, зарезервированные имена (`CON`, `NUL`, …)
  получают префикс `_`.
- `unlim_worker.safe_extract_dst` очищает каждый компонент имени из архива
  (после отбрасывания `..`, ведущих слэшей и буквы диска).
- `match_extracted` сравнивает уже очищенные имена, поэтому файл с `>` в
  имени находится в архиве под `_`.
- `relocate._Index` строит третий индекс `by_safe` по очищенному имени:
  «Файлы переехали?» находит и такие файлы.
