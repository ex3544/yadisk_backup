## 1. О проекте и текущее состояние

Проект: **Yandex.Disk Backup** — полная резервная копия Яндекс.Диска (обычные папки + раздел «Безлимит» с мобильными фото/видео) с локальным веб-интерфейсом.

- Активная рабочая папка на этой машине: `C:\Users\<user>\yadisk_backup_3544`
- Git-ветка: `main` — рабочая и публикуемая. Ветку `fix/audit-2026-08` не публиковать: в её локальной истории остался старый токен.
- Две базы SQLite: `state.db` (диск, таблица `files`) и `unlim_state.db` (безлимит, таблица `unlim_files`)

### Пути программы и данных (этап подготовки установщика)

Все пути собраны в [`paths.py`](./paths.py), модули больше не строят их из `__file__`:

| Что | Где |
|---|---|
| Программа (`APP_DIR`) | рядом с exe в сборке; папка проекта при запуске из исходников |
| Данные (`DATA_DIR`) | установленная версия: `%LOCALAPPDATA%\YandexDiskBackup`; исходники: папка проекта, если там уже есть `.env`/`state.db`/`cookies.json` |
| Переопределение | переменная `YADISK_DATA_DIR` (её же передаёт WebUI дочерним задачам) |
| Базы, `.env`, куки | `DATA_DIR/state.db`, `DATA_DIR/unlim_state.db`, `DATA_DIR/.env`, `DATA_DIR/cookies.json` |
| Логи и статусы | `DATA_DIR/logs/` |
| Скачанное по умолчанию | `D:\YandexDiskBackup\Disk` и `D:\YandexDiskBackup\Unlim`, если есть диск `D:`, иначе `%USERPROFILE%\YandexDiskBackup\...` |

Схема БД версионируется через `PRAGMA user_version` в [`db_migrations.py`](./db_migrations.py). Перед первой миграцией существующей базы автоматически создаётся копия `*.db.bak_v<версия>_<дата>`; миграция выполняется в транзакции. Схема «Безлимита» вынесена в [`unlim_schema.py`](./unlim_schema.py), чтобы `unlim_backup.py`, `unlim_download.py` и `unlim_worker.py` использовали одну историю.

### Первый запуск и диагностика (этап 2)

### Оконный режим и трей (этап 3)

- [`launcher.py`](./launcher.py) — точка входа собранного приложения. Поднимает uvicorn в фоновом потоке, открывает окно pywebview (Edge WebView2), держит значок в трее.
- Кнопка закрытия окна **сворачивает в трей**, а не завершает процесс. Полный выход — «Выход» в трее: останавливает задачи (`webui.tm.stop_all()`), сервер, трей и окно.
- Окно слушает `127.0.0.1`; порт 8000 или следующий свободный (до 12 попыток). Если приложение уже запущено, второй экземпляр открывает браузер на существующем URL.
- `WEBUI_HOST`/`WEBUI_PORT` переопределяют адрес. CSRF-проверка (`webui.origin_allowed`) разрешает same-origin на любом порту, чужие Origin по-прежнему блокируются.
- Если WebView2 не поднялся, приложение открывается в браузере, трей остаётся. Если недоступен и трей — показывается ошибка.
- В windowed-сборке `sys.stdout`/`stderr` перенаправляются в `logs/launcher_output.log`; собственный журнал — `logs/launcher.log`. Оба входят в диагностический отчёт.
- Стандартное контекстное меню WebView2 включается точечным патчем `launcher.enable_webview_context_menu()`: pywebview отключает его в не-debug режиме, из-за чего в полях ввода не работала вставка правой кнопкой. Devtools и горячие клавиши браузера при этом остаются выключенными.
- В «Организации» кнопка «Остановить» изначально `disabled` и активируется только при запущенной сортировке (`updateOrganizeControls()` в `webui_assets/index.html`).
- На «Главной» два визуально разных блока запуска: `.launch-card.auto` («Быстрый запуск: скачать всё», Диск + Безлимит, 1 клик) и `.launch-card.manual` («Пошаговый режим», только выбранный раздел). Под каждой кнопкой — `.btn-hint`; при запуске подсказки прячутся вместе с кнопками через обёртки `ctrl-*-wrap`.
- [`assets/`](./assets) — `app.ico`, `app.png`, `tray.png`; пересобираются `python tools/make_icons.py`.
- `webui.WORKER_SCRIPTS` + `webui.dispatch_worker()` — multi-call режим: `<exe> main.py scan`, `<exe> unlim_backup.py ...` и т.п. В frozen-режиме `TaskManager` запускает тот же exe с именем скрипта и рабочим каталогом `DATA_DIR` (Program Files только для чтения).
- [`yadisk_backup.spec`](./yadisk_backup.spec) собирает **onedir** `dist/YandexDiskBackup/YandexDiskBackup.exe`, `console=False`, с иконкой и ресурсами WebView2.

Не сбрасывайте `failed → pending` массово без явной просьбы пользователя: мёртвые файлы возвращаются в очередь и тормозят выгрузку.

Выгрузка шла на сменные диски, поэтому файлы распределены по нескольким носителям. Источник истины о расположении — поле `local_path` в базах:

|---|---|---|---|---|

| `D:/Unlim` | `unlim_state.db` | 23 171 | 1360,79 ГБ | массив безлимита на диске D: |
| `/media/vb/backup Ya1/Unlim` | `unlim_state.db` | 23 110 | 87,56 ГБ | история с прежней Linux-машины (на этом ПК этого пути нет) |
| `C:/NeUnlim` | `state.db` | 10 | 0,02 ГБ | новая выгрузка после переезда на C: |
| `C:/Unlim` | `unlim_state.db` | 29 | 14,29 ГБ | новая выгрузка после переезда на C: |

Диски на этой машине (на момент обновления документа):
- `D:` — 931,5 ГБ всего, занято 925,7 ГБ, **свободно ~5,8 ГБ** (папки `NeUnlim`, `Unlim`)
- `C:` — 238,4 ГБ всего, занято 82,2 ГБ, **свободно ~156 ГБ** (папки `C:\NeUnlim`, `C:\Unlim`)

Поэтому **новые файлы сейчас качаются на `C:`** (`.env`: `DOWNLOAD_DIR=C:\NeUnlim`, `UNLIM_DIR=C:\Unlim`, для безлимита `--out-dir "C:/Unlim"` передаётся явно).

В базах зафиксирован каждый файл и его статус. **При повторном запуске ничего повторно не скачивается — скрипты продолжают с оставшихся `pending` файлов.**

## 2. Авторизация (токен и куки)

Все ключи доступа уже находятся внутри папки проекта:

1. **Токен OAuth (`.env`):**
   - Переменная `YA_DISK_TOKEN` уже заполнена и валидна. **Никогда не выводите её значение в чат, логи или документы.**
   - Используется официальным REST API Яндекс.Диска (обычные папки).
2. **Сессионные куки (`cookies.json`):**
   - Используются для раздела «Безлимит» (мобильные фото/видео, которые REST API не отдаёт).
   - Если куки истекли: экспорт через расширение Cookie-Editor / J2TEAM Cookies в `cookies.json`, либо `python fetch_cookies.py` (Playwright, открывает браузер и снимает куки после ручного входа), либо `python extract_cookies.py`.
   - `fetch_cookies.py` также запускается из веб-интерфейса как фоновый процесс и пишет статус в `logs/cookies_fetch_status.json`.

`.env` и `cookies.json` в `.gitignore` — в репозиторий не попадают.

## 4. Пошаговое руководство для ИИ-агента на новом компьютере

### Шаг 1. Определите пути

На новом ПК путь к диску изменится. Проверьте/обновите `.env` (значение токена берите из существующего `.env`, не из документации):

```env
YA_DISK_TOKEN=<токен из .env>
DOWNLOAD_DIR=<ПУТЬ>/NeUnlim
DISK_DIR=<ПУТЬ>/NeUnlim
UNLIM_DIR=<ПУТЬ>/Unlim
MAX_WORKERS=4
LOG_LEVEL=INFO
```

Пути также задаются в WebUI на вкладке настроек. Начиная с этапа 1 `.env`, базы и куки читаются из `DATA_DIR` (см. таблицу выше), а не обязательно из папки скриптов. Для переноса данных на другой диск можно задать `YADISK_DATA_DIR` — тогда программа останется в `Program Files`, а состояние будет лежать в указанной папке.

### Шаг 2. Запуск окружения

- **Windows:** двойной клик по `webui.bat` (или `setup.bat`, если Python ещё не установлен) — скрипт проверит Python, поставит зависимости и поднимет дашборд.
- **Linux/macOS:** `bash webui.sh`.

### Шаг 3. Продолжение загрузки

- Откройте `http://localhost:8000` — на дашборде видно, сколько скачано/пропущено/осталось.
- Кнопки «Скачать диск» / «Запустить всё» продолжают с `pending`.
- В консоли эквивалент:
  ```bash
  # обычный диск (сбрасывает failed → pending и качает)
  python main.py retry-failed --workers 4
  # безлимит: сначала pending, затем один проход skipped
  python unlim_backup.py --target all --media all --out-dir "<ПУТЬ>/Unlim" --workers 4
  ```
- Чтобы обновить список упавших файлов для отчёта: `python report_status.py` → `logs/download_report.md`.

### Особенности этой машины

- В PATH `python` — это **шим PyManager**, а не рабочий интерпретатор. Реальный Python:
  `C:/Users/<user>/AppData/Local/Python/pythoncore-3.15-64/python.exe` (Python 3.15).
- ОЗУ всего ~5,9 ГБ. `auto_workers()` даёт **3 потока**; явный `--workers 4` переопределяет. При нехватке памяти системный «репер» Claude Code может снять фоновые процессы — не поднимайте их автоматически без просьбы пользователя.
- В проекте есть `memcheck.py` для сторожевых проверок ОЗУ и стандартная проверка свободного места через `shutil.disk_usage`.

## 5. Важные технические нюансы и эксплуатационные правила

- **Пожары в хранилищах Яндекса (2026):** часть серверов `*.storage.yandex.net` уничтожена. Проявления: `InternalServerError: Status code: 500`, `Read timed out`, `IncompleteRead`, а также «сочащиеся» шарды — соединение есть, байты идут крайне медленно, `iter_content` не рвётся. Для последнего в `unlim_backup.py` введён дедлайн на файл `max(120, timeout * 60)` сек (~420 сек при `--timeout 7`): по его истечении файл помечается `skipped`, поток освобождается.
- **Стратегия:** недоступные файлы помечаются `failed`/`skipped` с причиной; повторные проходы (`main.py retry-failed`, `unlim_backup.py --target skipped|all`) запускаются периодически, чтобы подобрать то, что Яндекс восстановил. **Не сбрасывайте `failed → pending` без явной просьбы** — кроме команды `retry-failed`, которую пользователь запускает осознанно.
- **Число потоков:** обычный диск — 4–5 максимум (иначе 429 Too Many Requests). Безлимит — 4 и меньше на машинах с малым ОЗУ.
- **Свободное место:** `downloader.py` перед каждым файлом проверяет `size + 50 МБ`; при нехватке файл получает `disk_full` и скачивание прерывается. Крупные файлы (например, zip на ~21 ГБ) на почти полном диске не влезают — нужен свободный носитель.
- **Файловая система:** NTFS/exFAT; пути нормализуются (`utils.py`), длинные пути экранируются префиксом `\\?\` на Windows.
- **Базы данных:** не удаляйте `state.db` и `unlim_state.db` — в них реестр уже скачанных файлов.
- **Логи:** `logs/unlim_backup.log` бывает очень большим (сотни МБ). **Не усекайте и не ротируйте его без явного согласия пользователя.**
- **Секреты:** никогда не выводите `YA_DISK_TOKEN` и содержимое `cookies.json`.
